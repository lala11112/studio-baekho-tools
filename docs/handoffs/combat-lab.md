# 도구 인계 — Baekho Studio / Combat Lab

현재 저장소에서 확인되는 도구인 **Combat Lab(타격감 찾기 자동화)**을 기준으로 작성했다. Baekho Studio는 이 도구를 제공하는 Windows 데스크톱 앱이다. 모델링 자동화는 현재 구현 범위로 확인되지 않아 포함하지 않았다.

[연결 구조·통합 안내](../desktop-bridge.md) · [다른 프로젝트 연결 가이드](../reusing-combat-lab.md) · [기존 검증 기록](../four-tiger-sword-analysis.md) · [프로젝트 안내](../../README.md)

> 확인 기준: 2026-10-08(한국 시간), 저장소 커밋 `9abf283`의 문서와 코드. 이번 작성에서는 문서·코드를 정적으로 확인했으며 앱 조작, AI 호출, Unity 실험, 자동 테스트는 **미실행**이다. 기존 문서에 기록된 실행 검증은 이번 확인과 구분했다. 템플릿의 `docs/tool-integration.md`, `docs/ux-principles.md`는 현재 저장소에서 찾지 못했으므로 해당 문서의 준수 여부는 미확인이다.

## 기본 정보

- 도구 이름: **Combat Lab — 타격감 찾기 자동화**. 제공 앱은 Baekho Studio이며, 현재 [앱 버전](../../Desktop/package.json)은 `0.6.0`, [Unity 공통 패키지](../../Packages/com.studiobaekho.combat-lab/package.json)는 `0.2.0`이다.
- 도구 설명과 주요 사용자 작업: 원하는 타격감을 글로 입력하고 동작별 AI 수치 후보 2~12개를 생성한다. Unity에서 후보별 자동 플레이·녹화를 실행하고 영상·피해 이벤트·실제 적용값을 비교한다. 사용자는 선호 후보와 이유를 저장하고 새 프리셋 또는 여러 동작을 합친 폼 ScriptableObject(SO)를 내보낸다. AI는 수치를 제안하며 자동 플레이는 규칙 기반이다. 영상의 타격감을 AI가 평가하는 반복 개선 기능은 없다.
- 작성일·마지막 확인일: **2026-10-08 / 2026-10-08**. 문서와 코드 확인일이며 이번 실제 동작 시험일은 없다.
- 인계 책임 역할·확인 경로: **담당 역할·담당자 배정 미정**. 기술 확인 경로는 앱 화면·로컬 파일 처리 `Desktop`, 공통 실행·녹화 `Packages/com.studiobaekho.combat-lab`, 게임 연결 `Integrations/FourTigerSword` 또는 `Integrations/Example`이다. 코드 경계는 확인했으나 조직의 책임 배정으로 해석하지 않는다.
- 현재 실행 방법·진입 위치: `Desktop/dist/0.6.0/Baekho Studio-win32-x64/Baekho Studio.exe`를 실행한다. 이번 확인에서 해당 파일의 존재를 확인했다. 배포 시 실행 파일이 들어 있는 폴더 전체가 필요하다. 앱의 **프로젝트 선택 → 실험 설계 → AI 후보 생성 → 후보 비교 실행 → 결과 비교** 순서로 사용한다. 개발 실행은 `Desktop`에서 `pnpm install`, `pnpm start --project 'Unity 프로젝트 루트'`이다. 기존 Unity의 `Tools → Baekho → Combat Lab` 편집 창은 현재 진입점이 아니다.
- 필요한 환경·설치·연결·권한: 배포 앱은 Windows x64용이며 Node.js 별도 설치 없이 실행하도록 구성되어 있다. 개발 환경은 README 기준 Node.js 22.12 이상·pnpm 11이다. Unity 패키지는 `6000.3`을 대상으로 하며 기존 문서의 검증 환경은 Unity `6000.3.10f1`, Four-Tiger-Sword, Input System `1.18.0`이다. 대상 프로젝트에 공통 패키지와 게임 어댑터를 설치하고 컴파일을 완료해야 한다. AI 생성에는 설치·로그인된 Codex CLI와 인터넷 연결이 필요하다. 실행에는 저장된 테스트 씬, Edit Mode, Reload Domain·Reload Scene 활성화가 필요하며 Four-Tiger-Sword는 플레이어·적·이동에 필요한 씬 구성이 필요하다. 녹화 중 Game View를 유지하고 Unity를 최소화하지 않는다. 프로젝트 결과·연결 폴더, 앱 설정, 임시 폴더 및 내보낼 `Assets` 경로에 필요한 파일 접근 권한이 있어야 한다. 현재 PC의 로그인·게임 설치·실행 준비 상태는 이번에 확인하지 않았다.
- 유지할 기존 UI와 내부 작업 순서: 프로젝트·모듈 표시와 최근 실험 목록, **실험 설계 / 결과 비교** 탭, 동작별 목표·후보 생성, 실행 조건, 동기 영상 비교, 판단 기록, SO 저장 흐름을 인계 기준으로 삼는다. 내부 순서는 **앱 요청 검증 → 프로젝트 내부 파일 통신 → Unity 브리지 → 공통 실행부 → 게임 어댑터 → 결과 파일 → 앱 비교 화면**이다. 현재 UI와 실행 책임을 다른 공통 앱에서 어디까지 그대로 유지할지는 별도 합의가 필요하다. 근거: [화면 구조](../../Desktop/renderer/index.html), [연결 구조](../desktop-bridge.md).
- 통합 방식·현재 단계: **구현된 범위**는 Electron 독립 앱, 로컬 Unity 파일 통신, Four-Tiger-Sword 어댑터, 독립 Example 어댑터, 실험·비교·내보내기이다. Unity 연결은 프로젝트의 `Library/CombatLabBridge`를 사용하며 외부 네트워크 API가 아니다. **문서상 확장 방향**은 Baekho Studio 안에 다른 개발 모듈을 추가하는 것이다. 별도의 공통 앱에 임베드하거나 공통 작업·결과 관리에 연결하는 방식, 일정, 승인 범위는 미확인이다.
- 전환 기간의 독립 도구 열기·공통 앱 복귀 경로: 독립 실행 파일을 새로 실행할 때 `--project` 인수로 프로젝트를 지정하거나 마지막 프로젝트 경로를 복원할 수 있다. 이미 앱이 실행 중이면 재실행은 기존 창에 포커스만 주고 새 `--project` 인수로 프로젝트를 바꾸지 않는다. 외부 공통 앱에서 특정 작업·결과로 진입하는 OS 딥링크와 복귀 링크는 현재 구현으로 확인되지 않는다. `baekho://`와 `baekho-media://`는 앱 내부 화면·영상 제공용이며 외부 인계용 영구 링크로 사용하지 않는다. 현재 앱 내부 복귀는 **실험 설계 / 결과 비교** 탭을 사용한다. 외부 공통 앱으로의 자동 복귀는 미지원이다.

## 입력·작업·결과 연결

- 필요한 프로젝트 문맥과 입력: Unity 프로젝트 루트, 어댑터 ID, 원본 SO의 GUID, 동작 ID, 해당 동작의 현재값·허용 범위, 원하는 느낌, 후보 수, 후보당 실행 시간 3~60초, 난수 시드, 녹화 여부가 필요하다. AI에는 목표·항목 설명·현재값·허용 범위를 전달하며 게임 소스나 플레이 영상을 분석하도록 전달하지 않는다. 전체 일반 콤보와 개별 일반 타격은 같은 데이터를 수정하므로 함께 선택할 수 없다. 현재 Four-Tiger-Sword는 다섯 속성의 일반 콤보·개별 타격·스킬·궁극기와 수 속성 강공격을 지원하되, 실제 선택 가능 여부는 현재 어댑터가 제공하는 사유와 데이터에 따른다.
- 작업 구분·다시 열기 방법: 실험마다 `runId`가 새로 만들어지며 형식은 UTC 시작 시각과 임의 식별자를 합친 `yyyyMMdd-HHmmss-xxxxxxxx`이다. 프로젝트를 선택한 뒤 왼쪽 **최근 실험**에서 실행 기록을 다시 연다. 목록은 유효한 보고서를 시작 시각 내림차순으로 표시하며 최근 N건으로 제한하는 구현은 없다. 작업 입력을 다시 편집·실행하려면 **JSON 불러오기**로 수동 저장한 JSON 또는 결과 폴더의 `request.json`을 연다. 결과를 보는 것과 실험 설계를 복원하는 것은 별개다.
- 보존하는 입력·설정·초안과 저장 시점: 마지막 프로젝트 경로는 프로젝트 선택 시 앱 `userData/settings.json`에 저장한다. 목표·동작별 후보·최종 후보 선택은 현재 화면의 메모리에 유지한다. 생성된 현재 동작은 **현재 동작 JSON 저장**을 눌렀을 때 요청 설정·후보·생성 정보를 파일로 보존한다. 실행 시작 시 요청과 원본 스냅샷 등을 결과 폴더에 기록한다. 선호 후보·이유는 **판단 기록 저장**을 눌렀을 때 `judgment.json`에 저장한다. **입력 초안 전체의 자동 저장은 없다.** 근거: [앱 설정·JSON 입출력](../../Desktop/src/main.cjs), [화면 상태·동작별 초안](../../Desktop/renderer/app.js).
- 복원하지 못하는 항목·저장 실패 시 안내: 후보 생성 전의 목표 초안, 저장하지 않은 후보·판단 이유, 여러 동작의 선택 구성과 최종 후보 선택 전체는 앱 재시작으로 복원되지 않는다. 프로젝트·원본을 바꾸거나 동작 선택을 해제하면 관련 메모리 초안을 잃을 수 있다. 결과를 전환하면 저장하지 않은 판단 입력도 초기화된다. JSON 저장은 유효한 후보가 준비된 현재 동작 단위이므로 생성 전 목표만 저장하거나 다중 작업 전체를 저장하는 대안은 아니다. JSON·판단 파일 저장 중 예외는 앱 오류 알림으로 전달되지만 저장 성공·자동 복구를 보장하지 않는다. 프로젝트 선택 중 설정 쓰기 오류도 앱 작업 오류로 전달된다. 앱 시작 시 설정 파싱·이전 프로젝트 경로 복원 실패는 콘솔에만 기록하며 별도 UI 알림은 없다. Unity 실행 보고서 저장 실패는 Console 오류와 남은 실행 중단으로 처리될 수 있어 결과 파일의 완전성을 별도로 확인해야 한다. 저장 완료 메시지를 확인하고 실패 시 권한·경로를 점검해 다시 저장해야 한다.
- 제공 가능한 실행 상태·확인 시점·진행 설명: 앱은 AI 연결·생성 중·취소 요청과 Unity 연결·컴파일·Play Mode·실행 상태를 구분한다. Unity 실행은 현재 후보 번호/전체 후보 수와 `entering`, `running`, `exiting` 등의 단계 문구를 제공한다. 화면은 약 1.5초 간격으로 갱신하되 다른 작업 처리 중에는 건너뛸 수 있다. Unity 상태가 15초보다 오래되면 다시 연결 중으로 표시하며, 컴파일·재로드로 인한 지연만으로 실패를 확정하지 않는다. 시작 응답은 실행 수락을 뜻하며 완료를 뜻하지 않는다. 후보별 보고서에는 `completed`, `no-hits`, `failed`, `cancelled`, `interrupted` 등이 기록될 수 있다. `no-hits`는 타격감 비교에 충분한 성공 결과로 해석하지 않는다.
- 사용한 도구 버전·실행 시점·결과 생성 시점의 제공 여부와 확인 방법: 현재 설치 소스의 앱·패키지 버전은 각 `package.json`에서 확인할 수 있으나 **실행별 보고서에 앱·공통 패키지·어댑터 버전을 기록하는 필드는 없다**. 실행별 Unity 버전과 시작 시각은 `report.json`의 `unityVersion`, `startedUtc`로 제공한다. AI 생성 시각·제공자는 `request.json`의 `generation.createdUtc`, `provider`로 제공한다. `model` 필드는 있으나 현재 생성 반환값은 모델명을 보장하지 않는다. 판단 저장 시각은 `judgment.json.createdUtc`로 제공한다. **실험 종료 시각·보고서 생성/갱신 시각을 명시하는 필드는 제공 불가**이며 파일 수정 시각으로 대체해 확정하지 않는다. 근거: [요청 계약](../../Packages/com.studiobaekho.combat-lab/Editor/CombatLabContracts.cs), [보고서 계약](../../Packages/com.studiobaekho.combat-lab/Editor/CombatLabReport.cs), [실행부](../../Packages/com.studiobaekho.combat-lab/Editor/CombatLabRunner.cs).
- 실패·중단 이유와 사용자가 할 수 있는 다음 행동: AI 연결·로그인·응답 검증 오류는 사유를 확인한 뒤 연결을 점검하고 다시 생성한다. 후보 수·목표·대상 변경으로 기존 후보가 유효하지 않으면 재생성한다. Unity 연결·컴파일·씬 저장·Play Mode 설정·동작 데이터 오류는 해당 조건을 수정한 뒤 처음부터 다시 실행한다. 실행 중 원본 데이터 변경이나 사용자 Play Mode 종료는 남은 실험을 중단할 수 있다. 요청 응답 시간이 초과되면 이미 실행되었을 수 있으므로 상태와 결과부터 확인한다. 자동 재전송이나 실패 지점부터 이어 실행하는 기능은 없다.
- 결과 구분·생성 작업·버전 구분 방법: 프로젝트 루트와 `runId`로 실험을, `adapterId`·`sourceGuid`·`actionId`로 원본/동작을, 후보 `id`로 후보와 영상을 구분한다. 후보 ID는 실험 안에서 사용하므로 전역 결과 ID로 단독 사용하지 않는다. `sourceDependencyHash`, 원본 스냅샷, 씬 의존성 해시, 요청값·실제 적용값을 비교할 수 있다. 별도의 결과 리비전·승인 버전 관리 체계는 없다. 같은 입력을 다시 실행해도 새 실험이며 동일 시드가 동일 전투를 보장하지 않는다.
- 결과 위치·보관 범위·접근 조건: 선택한 게임 프로젝트의 `CombatLabResults/<runId>/`에 아래 파일을 보관한다. 완료 결과 열람에는 Unity 연결이 필요하지 않지만 파일 접근 권한과 유효한 프로젝트 루트가 필요하다. 앱 내부 중앙 저장소나 클라우드 동기화는 없다. 자동 백업·보존 기간·삭제 정책은 확인되지 않았다. 이 저장소의 `.gitignore`는 `CombatLabResults/`를 제외하므로 Git 커밋만으로 결과 보관을 보장하지 않는다. 대상 게임 저장소의 보관 정책은 별도 확인해야 한다.

| `source-snapshot.json` | 시작 시 원본 에셋 스냅샷. 프로젝트 전체나 모든 의존 에셋의 백업은 아님 |
| `scene-dependency-hash.txt` | 시작 시 씬 의존성 해시 |
| `report.json` | 실행 식별·시작 정보, 후보별 상태·지표·실제 적용값·이벤트·경고. 실행 중 단계에 따라 갱신 |
| `<candidate-id>.mp4` | Windows에서 녹화한 후보 영상. 녹화 해제·실패·중단 시 없거나 불완전할 수 있음 |
| `judgment.json` | 앱에서 명시적으로 저장한 선호 후보·선택 이유·저장 시각 |
| `index.html` | 결과 영상과 함께 보관할 수 있는 기존 A/B 비교 보고서. 앱의 다중 비교 화면과 기능이 동일하지 않음 |
| 사용자가 지정한 JSON 파일 | 현재 동작의 요청을 수동으로 저장한 파일 |
| 사용자가 지정한 `Assets/.../*.asset` | 내보낸 새 프리셋 SO 또는 여러 동작을 합친 새 폼 SO. 실험 폴더와 별도로 생성 |

- 안정적인 결과 다시 열기 참조·위치 변경 시 처리: 현재 참조는 **프로젝트 루트 + `CombatLabResults/<runId>`**이다. 결과 폴더명과 `report.json.runId`가 일치해야 한다. 프로젝트 전체를 옮긴 경우 새 루트를 선택하고 같은 상대 구조를 유지하면 읽는 코드 구조이나, 이번 이동 시험은 미실행이다. 결과 폴더만 임의 위치로 옮기거나 이름을 바꾸면 자동 재연결하지 않는다. 원래 상대 위치·ID로 복구하거나 보관한 `index.html`과 영상을 사용한다. 내부 영상 URL은 임시 토큰이며 영구 참조가 아니다. 새 SO 내보내기는 경로·GUID를 응답하지만 실험 보고서에 지속적인 내보내기 이력으로 연결하지 않는다.
- 미리보기·편집·내보내기 등 결과 행동: 여러 후보 영상 동시 비교, 비교 개수 선택, 함께 재생·일시정지·탐색, 0.5×/0.25× 재생, 첫 명중 정렬, 한 후보 소리 선택, 지표·실제 적용값·이벤트 확인, 결과 폴더 열기, 선호 후보·이유 저장을 지원한다. 후보 수치는 읽기 전용이며 앱 안에서 직접 수치 편집·영상 편집을 하지 않는다. 요청 JSON 저장/불러오기, 단일 후보 새 프리셋 SO 저장, 지원 어댑터의 여러 동작 통합 SO 저장을 지원한다. 영상 정렬과 오디오 동기는 근사치이므로 프레임 단위 정확도를 보장하지 않는다.
- 실행 완료와 별도로 표시할 검토·보관·적용 상태: 현재 실행 상태와 사용자 판단 파일은 분리되어 있다. 다만 **검토 전/검토 완료, 보관 확인, 게임 적용 완료**를 각각 관리하는 상태 모델·UI는 없다. 결과 파일이 생성됐다는 사실, 사용자가 판단을 저장했다는 사실, SO를 내보냈다는 사실, 게임에 채택했다는 사실을 인계 시 구분해야 한다. SO 저장 성공을 게임 적용 완료로 표시해서는 안 된다. 상태 분리는 아래 개선 항목에 남겼다.
- 적용 대상·변경 내용·지원 제약: 실행 중에는 원본 복사본에 후보 값을 적용한다. Four-Tiger-Sword의 단일 내보내기는 선택 동작을 수정한 복제 폼을 포함하는 새 프리셋이며, 사용자가 그 안의 폼 SO를 플레이어의 해당 폼 참조에 연결해야 한다. 여러 동작 저장은 같은 원본 폼의 최종 후보를 합친 실제 폼 SO를 파일의 메인 객체로 생성하므로 해당 파일을 연결한다. 필요한 카메라 프로필 복사본은 하위 에셋에 포함하고 원본 SO·선택하지 않은 동작은 보존한다. 기존 파일 덮어쓰기는 거부하며 `Assets` 아래 존재하는 폴더의 새 `.asset` 경로가 필요하다. Unity 편집 모드와 호환 어댑터가 필요하고 서로 다른 원본 폼은 합칠 수 없다. **기존 게임 설정으로의 자동 반영은 미지원**이다. 상속된 히트스톱 값은 플레이어 없는 씬에서는 게임 선언 기본값을 사용하므로 실제 테스트 씬에서 생성·내보내는 것이 필요하다. 근거: [Four-Tiger-Sword 어댑터](../../Integrations/FourTigerSword/Editor/FourTigerCombatAdapter.cs), [적용 방법](../../README.md).

## 이동·실패 시 안내

- 현재 프로젝트·도구와 돌아갈 위치 표시: 사이드바에 프로젝트명·경로와 활성 Combat Lab 모듈, 상단에 `Baekho Studio / Combat Lab`, 화면에 두 작업 탭과 최근 실험이 있다. 결과 비교에서 실험 설계로 돌아갈 수 있다. 외부 공통 앱명·복귀 위치·프로젝트 문맥 전달 상태를 표시하는 기능은 현재 없다.
- 이동·종료로 작업이 멈추거나 입력을 잃을 때 안내할 내용: AI 생성 중이거나 연결된 Unity가 실행 중이면 프로젝트 변경을 제한하고 완료 또는 취소를 안내한다. **창 닫기 전 데이터 손실 확인, 원본 변경·동작 해제 전 초안 경고, 다른 결과로 전환하기 전 미저장 판단 경고는 현재 구현으로 확인되지 않는다.** 인계 시 “앱을 닫으면 AI 생성은 취소되고 저장하지 않은 입력은 사라지며, 이미 시작한 Unity 실험은 계속된다”를 전달해야 한다. 종료 전 사용자가 생성된 동작별 JSON·판단을 저장하고 Unity 실험을 계속 둘지 취소할지 선택하도록 하는 UI는 개선 필요다. 녹화 중에는 Unity와 Game View를 유지해야 한다.
- 실행을 유지할 수 없을 때 초안을 남기고 재개하는 방법: 실행 전 준비된 각 동작을 JSON으로 저장하고 판단은 별도 저장한다. 이미 시작한 요청은 결과 폴더의 `request.json`을 사용할 수 있다. 다시 열 때 같은 프로젝트·어댑터·원본을 확인하고 JSON을 불러와 **새 실험을 처음부터** 실행한다. 여러 동작의 선택 구성·최종 후보는 다시 구성해야 하며 생성 전 목표는 앱 안에서 파일로 저장할 수 없다. Unity 종료 후 실행 재개와 강제 종료 시 정상 복구는 보장하지 않는다.
- 접근 불가·미지원·조건 미충족 기능의 비활성 이유와 다음 행동: 프로젝트 미선택은 프로젝트 선택, Unity 미연결·컴파일 중은 올바른 프로젝트 열기와 컴파일 완료, Codex 미설치·미로그인은 설치·로그인, 데이터 없는 동작은 어댑터가 표시한 사유 확인, 후보 변경·범위 불일치는 재생성, 통합 저장 미지원은 어댑터 지원 확인, 서로 겹치는 동작은 선택 조정, 내보내기 조건 불충족은 Unity 편집 모드·새 파일 경로 확인으로 안내한다. 일부 사유는 화면 설명·오류 메시지에 있으나 모든 비활성 버튼에 개별 사유가 표시되는지는 실제 UI 시험이 필요하다.
- 결과가 삭제·이동되거나 접근 불가할 때 처리: `report.json`이 없거나 손상되면 목록에서 제외될 수 있고 직접 열기는 오류가 된다. `request.json` 누락·손상은 보고서 열람을 막지 않지만 해당 요청이 필요한 SO 내보내기를 제한한다. 유효하지 않은 `judgment.json`은 무시되어 저장된 판단이 없는 상태로 열린다. 영상 누락은 “이 후보의 녹화 영상이 없습니다”, 재생 실패는 “영상을 열 수 없습니다”로 표시한다. 접근 권한과 파일 존재를 확인하고 원래 결과 폴더·파일을 복구해야 하며 자동 위치 추적이나 삭제 복구는 없다. 목록에서 제외된 이유와 복구 행동을 직접 안내하는 기능은 개선 필요다. 근거: [결과 파일 처리](../../Desktop/src/project-client.cjs), [미디어 로딩](../../Desktop/src/main.cjs), [비교 화면](../../Desktop/renderer/app.js).
