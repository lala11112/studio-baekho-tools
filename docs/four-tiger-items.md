# 사인검 아이템 제작 도구

백호툴의 네 번째 도구 **사인검 아이템**에서 5오행 × 4등급 초안20개를 생성·편집하고 아이콘을 만들어 검토할 수 있습니다.

## 사용 순서

1. 홈 → 사인검 아이템 → **20개 초안 만들기**. 누를 때마다 별도 묶음을 만듭니다.
2. **누락 아이콘 생성** 또는 아이템의 **이 아이콘 생성**. 기존 Codex 로그인과 내장 imagegen으로 한 번에 1개씩 처리합니다. 별도 유료 API나 키를 쓰지 않습니다. 생성된 이미지는 자동 채택되지 않습니다.
3. 카드 또는 목록에서 이름·ID·효과·값·폼·지속시간·설명·아이콘 요청을 수정하고 저장합니다. UI의 8%는 JSON에서 0.08입니다. 등급 가격은20/40/80/160G로 자동 계산됩니다.
4. 효과를 수정하면 설명을 다시 생성하거나 직접 확인합니다. ID를 바꾸면 규칙 검사에서 참조를 갱신합니다.
5. 밝은/어두운 배경과64/128/256px에서 아이콘을 확인하고 버전을 고릅니다. **데이터 검토 완료**와 **아이콘 검토 완료**는 별도 동작입니다. 기존 이미지를 새 수치에 맞는 것으로 다시 검토할 수도 있습니다.
6. 제안 정책의 상한·하한·중첩·자원 변경 방식을 확인하고 명시 채택합니다. 아이템을 선택하여 채택 확인 화면을 통과합니다. 보류한 항목은 채택본 출력에서 제외 가능한 것이 아니라,20개 구성 조건을 만족할 때까지 전체 채택본 출력을 막습니다.
7. **초안 묶음 보관**은 미채택 제안과 누락 상태를 보존합니다. **채택본 Unity 데이터 출력**은20개 구성·현재 데이터·아이콘·정책 검토와 파일 검사를 모두 통과한 경우에만 가능합니다.

기본 source는 `lala11112/Four-Tiger-Sword`의 `codex/system-design-2026-10-07@fe533a25a0df81eb317059ee18708229d63320ad`입니다. 개별 이름·효과·수치·상한과 아이콘은 제안이며 확정 기획과 구분됩니다. `main` 기획으로 대체하지 않습니다.

## 저장·실패 복구

도구의 데이터는 백호툴 데이터 루트 아래 `four-tiger-items/<묶음 UUID>`에 저장됩니다. Windows 기본 위치는 기존 앱의 데이터 위치를 따릅니다. 검증 실행은 항상 별도의 `BAEKHO_DATA`를 사용합니다.

- 저장 충돌이면 최신 파일을 불러오되 입력 중 편집 내용은 유지합니다. 내용을 확인한 후 다시 저장합니다.
- 손상된 묶음은 목록에 표시됩니다. **이전 정상본 복구**는 명시 확인 후 실행하며 손상 파일을 별도로 보존합니다. 지원하지 않는 미래 데이터 형식은 복구로 덮어쓰지 않습니다.
- 생성 요청은 실행 전에 기록합니다. **남은 작업 취소**는 대기분을 취소합니다. 이미 생성 중인 작업을 중복 요청하지 않습니다.
- 중단·불명 결과는 **기존 결과 복구**로 기록된 작업 폴더를 확인합니다. 결과 유무가 불명확한 요청을 자동 재시도하지 않습니다. 유효 파일이 발견되어도 현재 내용을 자동 검토·채택하지 않습니다.
- 아이콘은 원본 PNG와 검증된256px PNG, 파일 해시, 생성 시 내용 revision을 보관합니다. 수정 중 도착한 이전 결과는 보존되지만 자동 선택하지 않습니다.

## 출력과 Unity 범위

매번 새 폴더에 `saingeom-items.v1.json`, `icons/*.png`, `manifest.json`, `validation-report.json`, `README.md`를 씁니다. 초안은 `review-bundle`, 채택본은 `exports` 아래에 저장됩니다. 기존 게임 에셋을 덮어쓰지 않습니다.

지정한 사인검 기획 브랜치와 확인한 코드에는 이번 데이터에 대응하는 `ItemDefinition`/아이템 ScriptableObject/importer가 없습니다. 따라서 존재하지 않는 타입을 가정하지 않고 JSON+PNG를 출력합니다. Unity는 JSON을 TextAsset, PNG를 Texture2D/Sprite로 반입할 수 있습니다. **실제 게임의 아이템 소지·전투 효과 적용은 연결되지 않았습니다.** 기존 전투 도구의 E스킬/R궁극기와 새 기획의 숫자 폼전환/E상호작용 차이도 이번 범위 밖입니다.

## 개발 검증

```powershell
npm test
npm run test:combat
npm run test:hit-timer
npm run build
npm run test:integration
node scripts/four-tiger-items-smoke.mjs --mode fixture
node scripts/four-tiger-items-smoke.mjs --live
node --import tsx scripts/four-tiger-items-unity-smoke.ts --unity '<Unity.exe>' --package '<출력 폴더>' --project '<존재하지 않는 새 테스트 폴더>'
```

`--mode fixture`는 명백한 테스트 PNG만 사용하고 실제 생성 성공으로 집계하지 않습니다. `--live` 화면 검증은 `.local/four-tiger-live-state.json`이 가리키는 실제 초안을 **새 격리 폴더에 복사**한 뒤 검토·채택·출력하며 원본 제안의 상태를 바꾸지 않습니다. 실제 생성은 제품 API와 동일한 `FourTigerIconQueue` / `CodexFourTigerIconRunner`를 사용합니다.

Unity 검증기는 신규 프로젝트에 빈 패키지 목록을 사용하여 패키지 설치 없이 실행합니다. 기존 프로젝트를 재사용하지 않으며 입력 폴더가 이미 존재하면 실패합니다. `tests/unity/FourTigerItemPackageImportCheck.cs`는 테스트 프로젝트 전용 코드입니다.
