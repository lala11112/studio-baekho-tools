# Four-Tiger-Sword 전투 실험 연결 분석

분석 기준: 2026-10-08. 게임 저장소에 이미 여러 미커밋 변경이 있어 현재 파일 내용을 기준으로 연결하며, 기존 게임 스크립트/에셋의 수정은 피했습니다.

## 폼 SO 그룹 구조 대응 (0.5.0)

현재 어댑터는 `WeaponActionDataSO.Actions`, `CommonBalance/CommonExecution/CommonFeedback`, 각 폼의 `FormBalance/FormExecution/FormFeedback`, 공격과 HitEvent의 `Balance/Execution/Feedback`을 사용합니다. 아래의 첫 구현과 이전 검증 기록은 변경 전 동작을 설명하는 이력입니다.

히트스톱의 실제 우선순위는 활성 개별 타격 override → 공격 override → 플레이어 기본값입니다. 기존 플레이어 공통값 조정은 새 override에 가려질 수 있어, 이제 선택한 공격 복사본의 `Feedback.HitStop`과 활성 개별 override에 후보 길이를 기록합니다. 원래 유효 timeScale과 다른 동작은 보존합니다. 내보낸 폼 SO에 히트스톱 설정이 포함되므로 게임에 채택할 때 플레이어 공통값을 별도로 바꿀 필요가 없습니다.

수 궁극기는 첫 단계에서 10회 타격에 사용하는 설정을 읽습니다. 수 강공격과 토 스킬처럼 개별 HitEvents를 사용하지 않는 경로도 실제 게임 코드에 맞춰 처리합니다. 폼 특수값은 그룹의 실제 필드에서 결과에 기록하므로 호환 프로퍼티로 바뀐 뒤 누락되던 값도 표시됩니다. 후보의 히트스톱 한 값은 선택 동작 전체에 적용하며, 기준 표시는 첫 유효 타격을 사용합니다.

다른 프로젝트 연결은 [재사용 가이드](reusing-combat-lab.md)를 참고하세요. 공통 패키지에는 Four-Tiger-Sword 타입 의존성이 없고 독립 예제 어댑터가 포함됩니다.

0.5.0 검증 결과: Unity 6000.3.10f1 컴파일 성공, 그룹 구조 57개·공통 요청 24개·5개 폼/30개 동작 341개·브리지 11개·세션 복원 119개·30개 동작 세션 902개 검사 통과. 실제 입력 실행도 수 일반 콤보/궁극기/강공격, 토 스킬, 화 궁극기, 목 스킬 모두 완료 및 피해 이벤트를 확인했습니다. 이 실행 검사는 녹화를 끄고 수행했습니다. 별도의 배포 앱 진단에서는 기존 MP4 세 개의 비교·재생·탐색을 검증했습니다. 새 구조 회귀 검증 전후 원본 폼 SO 5개와 Game Scene 파일 해시가 동일했고, 종료 시 편집 모드와 저장된 씬 상태로 복귀했습니다. 데스크톱 테스트는 76개 통과했습니다.

## 실행 경로

`PlayerInputHandler`는 Input System 입력을 읽어 `AttackBuffer`, `AttackPressId`, `IsAttackHeld`, `AttackHeldTime`을 갱신합니다. `PlayerStateMachineSetup`이 공격 상태로 전환하고 `PlayerAttackState`가 현재 폼의 공격 함수를 호출합니다. `BaseForm.Actions`는 `Time.deltaTime * AttackSpeed`로 공격 타이머를 진행하고, `BaseForm.Hit`가 물리 판정 후 `DamageManager.Apply`와 `Enemy.TakeDamage`를 호출합니다.

## 설정 위치와 실험에서의 의미

| 위치 (Assets/_Project/Scripts 기준) | 의미 / 연결 방식 |
|---|---|
| NewPlayer/WeaponActionDataSO.cs | 공격, 스킬, 필살기와 연출을 담는 기본 SO |
| NewPlayer/WeaponActionData.cs | 타수, 다중 타격, 이동, 넉백, 카메라 설정이 섞인 직렬화 데이터 |
| FormActions/WaterFromAction.asset | 첫 대상. 실제 파일명은 WaterFromAction |
| NewPlayer/PlayerController.cs | 컴포넌트에 전역 히트스톱 시간/배율 저장 |
| AttackCameraProfile.cs | 별도 참조 SO. 변경할 때 복제 필요 |
| Enemy/DefaultEnemy/EnemyData.cs | 넉백 시간/최대 이동 거리. 공격의 초기 속도와 함께 결과를 결정 |

수 속성 첫 공격은 분석 당시 `Water1`, Duration 1.433초이며, .43/.63초에 개별 HitEvent가 실행됩니다. 기본 HitStartTime과 Damage를 바꿔도 다중 타격 경로가 우선하여 효과가 없을 수 있습니다. 개별 타격 넉백 override가 켜져 있어 도구는 실제 활성 override도 함께 변경합니다.

공통 타격 경로는 카메라 프로필이 있으면 복제한 HitImpulse를, 없으면 CameraShakeStrength를 사용합니다. 다른 동작이 같은 카메라 에셋을 참조하더라도 선택한 동작의 참조만 복제하여 변경합니다. 수 궁극기는 별도 경로로 CameraShakeStrength만 사용합니다.

## 수명주기

PlayerController.Awake가 모든 폼을 생성하고 각 폼은 SO 참조를 보유합니다. 그 후 플레이어의 SO 필드만 바꾸면 이미 생성된 폼에는 반영되지 않습니다. 어댑터는 일반 상태에서 선택한 속성의 새 폼과 SO 복사본을 연결합니다. 후보마다 Play Mode를 새로 시작하여 누적된 상태를 제거합니다.

FormManager는 등록 폼을 계속 보관하므로 세션 종료 시 도구가 삽입한 폼만 해제하고 이전 폼으로 복구합니다. 입력 참조·활성 상태와 가상 장치를 복구/정리합니다. 연결할 공개 API가 없는 private serialized 필드와 등록 폼 집합은 프로젝트 전용 어댑터에서 제한적으로 reflection을 사용하며, 이름/형식 변경 시 사전 오류로 중단합니다.

## 첫 구현의 범위

- 수 속성 일반 공격 전체의 넉백·카메라 임펄스 배율, 플레이어 공통 히트스톱 시간.
- 가장 가까운 살아 있는 적을 향한 단순 이동과 탭/콤보 입력. 장애물 우회와 회피는 없음.
- 원본 InputAction 에셋을 복제하여 가상 키보드·마우스로 제어. 실제 PlayerInputHandler/StateMachine을 통과.
- 느린 녹화 프레임이 강공격 홀드로 해석되지 않도록 실행 복사본의 강공격 홀드 임계값만 실험 시간보다 크게 설정. 저장한 후보 SO에는 이 정책 변경을 반영하지 않음.
- Enemy.OnDamaged로 실제 피해 관측. EnemyStat.OnDamageTaken은 현재 활성 피해 경로에서 발생하지 않아 사용하지 않음.
- 정확한 타수별 명중률/콤보 성공률은 계산하지 않음. 모든 관측된 적 피해에는 보조 효과가 섞일 수 있음.

## 녹화와 비교

Recorder 5.1.7의 RecordingSession은 게임 시간과 timeScale로 프레임 시간을 계산합니다. 이 게임의 전역 히트스톱(timeScale=0)에 적합하지 않아 Unity Editor MediaEncoder에 실제 경과 시간으로 프레임을 전달합니다. 원본 Recorder 패키지를 수정하지 않습니다.

렌더된 Game View를 캡처하므로 녹화 중 해당 뷰가 렌더되어야 합니다. 녹화 부하는 플레이 프레임과 전투 결과에 영향을 줄 수 있습니다. 영상은 성능 벤치마크가 아닙니다. 프레임 단위와 첫 명중 정렬은 관측 시점 기준이며 서로 다른 전투 결과를 동기화된 동일 사건으로 보장하지 않습니다.

2. 후보당 반복 횟수와 여러 시드, 사건별 명중/콤보 이벤트 연결.

4. 프리셋을 직접 플레이하는 모드, 선택 설정의 원본 적용 diff/Undo.
5. 두 번째 프로젝트 어댑터로 공통 계약 검증.

## 독립 앱으로 분리

같은 날 사용자 요청에 따라 Unity 편집 창을 제거하고, 독립 Windows 앱 `Baekho Studio`로 후보 편집·실행·기록·영상 비교·판단 저장·프리셋 내보내기를 옮겼습니다. Unity 연결은 `Library/CombatLabBridge`의 파일 요청과 응답으로 실행되며 에디터 창에 의존하지 않습니다. 자세한 계약은 [데스크톱 연결 문서](desktop-bridge.md)에 있습니다.

외부 앱에서 실행하자 Input System이 Game View 포커스 밖의 가상 입력을 무시하는 문제가 확인되었습니다. 세션이 임시 InputSettings 복사본을 사용하도록 수정했으며, 종료 시 원래 참조를 복원합니다. 입력 설정 원본은 수정하지 않습니다.

- 앱 파일 접근·프로젝트 전환·명령·영상·판단 저장 검사 31개 통과. 영상의 실제 바이트 범위 요청·취소 검사 포함.
- Unity 연결 프로토콜 회귀 검사 11개 통과.
- 입력 설정 복원 검사를 추가한 Play Mode 세션 정리 검사 118개 통과.
- 외부 앱에서 요청한 실험 `20261008-053004-a2f5d2c1`: 두 후보 각각 10초, 완료 상태, 명중 14회/16회, 영상 생성과 앱 내 디코딩 확인.
- 실험 후 씬 dirty=false, 원본 SO 해시 유지, Unity 오류 로그 0건.
- Windows 배포본 0.2.1에서 기본 A/B 선택, 두 영상 동시 재생·일시정지, 첫 명중 정렬, 시간 이동과 1280×720 디코딩 검증 통과. 1024×800 창에서도 가로 넘침 없음, 렌더러 오류 0건.

Windows 앱은 Electron 실행 파일과 동봉 파일을 포함하는 portable 폴더로 배포합니다. UI와 이력 열람은 독립 실행되며, 새로운 플레이·녹화·SO 생성은 열린 Unity Editor를 사용합니다.

## AI 수치 생성과 여러 후보 비교

0.3에서는 수동 수치 입력을 제거하고 로그인된 Codex CLI가 목표 문장과 현재 항목·범위를 받아 수치를 생성합니다. 후보 수는 사용자가 2~12개로 지정하며 전체 후보를 AI가 작성합니다. 실패 시 고정 배율이나 난수로 대체하지 않습니다. 기존 자동 플레이 정책은 그대로 사용합니다.

실제 검증 실행 `20261008-061001-45a2641a`에서 Codex가 후보 4개를 작성했고, 각 후보를 4초씩 실행했습니다. 네 후보 모두 completed이며 각각 6회 명중이 관측됐습니다. 생성 목표·후보 수·생성 시각과 후보별 제안 이유가 Unity 재로드를 거쳐 request/report에 유지됐습니다. 이 결과는 수치 제안의 타격감 우열을 입증하지 않습니다.

- 앱 회귀 검사 57개 통과: 실제 AI 응답의 스키마·범위·개수·중복 검증, 생성 취소와 실패, 목표/개수 변경 후 재생성 요구, 1/3/7/12개 비교 구성과 기존 기록 호환 포함.
- 실제 AI 호출 → 읽기 전용 후보 표시 → UI에서 실험 시작 → 네 영상 디코딩 → 동기 재생·탐색·첫 명중 정렬·음성 선택 검증 통과.
- 비교 개수 4 → 2 → 4 변경과 중복 후보 선택 교환 확인. 1024×800 창에서 가로 넘침 없음, 렌더러·Unity 오류 0건.

실제 수치 생성은 온라인 Codex 모델을 사용합니다. 영상 내용을 AI가 판단하거나 사용자 피드백을 다음 생성에 자동 반영하는 단계는 아직 연결하지 않았습니다.

## 다섯 속성과 동작 선택 (0.4)

수·화·목·금·토의 실제 SO를 탐색하여 전체 콤보 5개, 개별 일반 타격 14개, 수 강공격 1개, 스킬 5개, 궁극기 5개로 총 30개 동작을 제공합니다. 강공격은 현재 게임에서 수 폼만 구현되어 있어 나머지 네 폼에는 사용할 수 없는 이유가 표시됩니다. 공중 공격과 반격 시나리오는 아직 제공하지 않습니다.

| 대상 | 실제 조정 항목 / 재생 방식 |
|---|---|
| 일반 콤보·개별 타격·수 강공격·수/화/토/금 스킬·금 궁극기 | 해당 단계의 넉백·적중 카메라·공통 히트스톱 |
| 목 스킬 | 끌어모으기 범위·속도·피해. 일반 타격 피드백 경로를 사용하지 않음 |
| 수 궁극기 | 범위·CameraShakeStrength·히트스톱. 게임의 10회 타격 로직 유지 |
| 화 궁극기 | 주는 피해·공격 속도·받는 피해 증가율. R 후 일반 콤보 |
| 토 궁극기 | 방어막·버프 시간·피해 증가율. R 후 일반 콤보 |
| 목 궁극기 | 침묵 영역 범위·시간·속성 피해 증가율. R 후 일반 콤보 |

SO에 있는 필드라도 게임이 읽지 않는 항목은 제외했습니다. 예를 들어 화 궁극기 체력 소모 필드는 현재 실행 코드에서 참조하지 않습니다. 수 스킬의 HitDuration은 동작 Duration보다 길지만 게임이 판정 시간을 동작 끝으로 제한하므로 정상적인 설정으로 인정합니다. 애니메이션 이름이 비어 있는 스킬은 기존 게임의 동작을 그대로 실행합니다.

요청·보고서·프리셋은 `actionId`를 보관합니다. 개별 타격은 실행 복제본만 한 단계 콤보로 만들며, 저장하는 프리셋은 전체 콤보 구조를 유지합니다. 스킬 SP, 궁극기 게이지, 수 강공격 충전은 실험 시작 때 준비하고 재사용 대기시간과 소모 규칙은 유지합니다. 선택 동작의 상태 진입과 실제 단계는 `action-executed`, 버프 뒤 일반 공격은 `follow-up-attack`으로 구분합니다.

같은 날 실제 Game Scene 검증:

- 앱 검사 65개, 공통 요청 검사 24개, 브리지 검사 11개 통과.
- 동작별 복제·검증·내보내기 검사 341개 통과. 5개 원본 SO 파일의 SHA-256 유지.
- 새 동작 세션 검사 840개 통과: 30개 동작의 입력 연결·자원 준비·복원. 기존 세션 복원 118개도 통과.
- 실제 플레이 13개 시나리오 통과: 다섯 스킬·다섯 궁극기·수 강공격·수 3타 단독·화 전체 콤보. 각각 선택한 동작의 실행과 피해가 관측됨. 이 검사는 타격감의 우열을 판정하지 않음.
- Windows 0.4.0 배포본에서 화 스킬 AI 후보 2개 생성 → 각 6초 플레이 → MP4 비교 완료. 실행 ID `20261008-064346-c03be0cc`, 후보별 명중 2회/3회, 스킬 실행 각 1회.
- 두 영상 모두 1280×720 디코딩·동기 재생·탐색·소리 선택 통과. 1024×800 가로 넘침 없음, 앱 렌더러·Unity 오류 0건.

## 여러 동작의 독립 후보 생성과 통합 저장 (0.6)

같은 폼에서 여러 동작을 체크하면 각각 목표·후보 수·AI 생성·비교 실행·최종 후보 선택 영역을 제공합니다. 각 동작에서 고른 후보를 원본의 복사본에 적용해 실제 폼 SO 하나를 메인 객체로 저장합니다. 별도 프리셋 래퍼가 없으며 필요한 카메라 복사본은 같은 파일의 subasset으로 포함합니다. 전체 콤보와 개별 일반 타격의 중복 선택은 거부합니다.

새로 그룹화된 `Actions`, `CommonBalance/CommonExecution/CommonFeedback`, `FormBalance/FormExecution/FormFeedback` 구조를 사용하는 현재 게임에서 검증했습니다.

- 앱 자동 검사 102개, Unity 통합 저장 67개·그룹 데이터 57개·공통 요청 24개·브리지 11개 통과.
- 실제 AI로 수 폼 일반 1타와 스킬의 후보를 각각 2개 생성했고, 다른 동작의 후보가 유지됨을 확인했습니다.
- 일반 1타 실행 `20261008-100232-e26aad20`: 후보마다 3초, 두 후보 모두 completed, 각각 4회 명중.
- 스킬 실행 `20261008-100305-ff7c369e`: 후보마다 3초, 두 후보 모두 completed, 각각 1회 명중. 이번 검사는 녹화를 끄고 실행했습니다.
- 결과 화면에서 일반 1타의 두 번째 후보와 스킬의 첫 번째 후보를 선택해 한 `.asset` 파일로 저장했습니다. Unity float32 직렬화로 생기는 소수점 표현 차이도 허용하며 실제 다른 값은 일치하는 후보로 취급하지 않습니다.
- Windows 0.6.0 배포본에서 실제 생성 JSON 불러오기 → 실제 실행 결과의 최종 후보 선택 → 새 폼 파일 하나 저장을 재확인했습니다. 렌더러 오류와 1024×800 가로 넘침은 없었습니다.
- 실제로 저장된 세 파일을 각각 51개 항목으로 검증해 선택한 배율·히트스톱과 변경하지 않은 동작·공통 설정이 맞는지 확인했습니다. 검증용 SO는 정리하고 결과 JSON을 보관했습니다.
- 원본 폼 5개와 저장된 Game Scene의 SHA-256이 유지됐습니다. 변경된 공통 패키지 0.2.0은 별도 프로젝트의 기존 Example 어댑터에서도 컴파일·SO 저장·두 후보 실행을 통과했습니다.

위 명중 횟수는 실행 연결을 확인하기 위한 한 번의 관측이며 후보 간 타격감 우열을 뜻하지 않습니다. 통합 저장은 선택한 각 동작의 후보 값을 모읍니다. 합쳐진 폼 전체의 전투 흐름은 저장된 폼을 플레이어에 연결하여 게임에서 확인할 수 있습니다.
