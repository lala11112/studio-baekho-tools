## 이번에 확인하고 수정한 앱 문제

### 새 프로젝트에서 대상 선택으로 이어지지 않던 진입

홈의 **새 오브젝트 만들기** 또는 **이미지·모델로 시작**에서 첫 프로젝트를 만들면, 아직 그래픽 작업공간 기록이 없어 대상 선택 모달을 열지 못했다. `GraphicsStudio`의 진입 처리가 모든 종류의 진입에 작업공간 존재를 요구한 것이 원인이었다.

새 작업과 가져오기는 작업공간 기록 없이도 대상 선택을 연다. 이어하기는 저장된 작업공간을 기다린다. 대상 선택을 취소하면 오브젝트 생성이나 제작을 시작하지 않는다.

- 기존 배포본에서의 재현: `artifacts/runtime/qa-20261018-app/workflow.json`.
- 수정한 소스 앱의 실제 진행: `artifacts/runtime/qa-20261018-app/workflow-source.json`.
- 실제 `App`과 `GraphicsStudio`를 함께 사용하는 회귀 검사: `tests/graphics-entry-intent-ui.test.ts`. 빈 프로젝트 목록과 빈 작업공간 목록에서 new/import 각각 프로젝트 생성 후 대상 선택, 선택 전 생성 차단, 취소 후 재진입 없음, 프로젝트 생성 외 명령 없음까지 확인했다. 화면 검사는 숨겨진 Electron의 DOM을 사용하며 운영체제 입력을 사용하지 않는다.

### 가져온 FBX의 화면 미리보기가 없던 문제

가져오기는 FBX 원본을 복사하고 해시를 기록했지만, 화면용 GLB 파생본을 준비하지 않았다. 그 결과 실제 FBX를 가져와도 미리보기 지원 불가 문구가 표시됐다.

기존 Blender 로컬 미리보기 파이프라인을 가져오기에 연결했다. FBX·BLEND·OBJ·STL은 원본을 유지하고 화면용 GLB와 원본 면 수 보고서를 별도로 만든다. GLB 원본은 직접 미리본다. BLEND를 열 때 자동 스크립트 실행을 비활성화한다. 새 모델 생성, 리깅 AI, 유료 API 또는 제작 GPT 호출이 아니다.

원본·동반 파일 해시를 처리 전후에 확인하고, 보고서의 원본 해시와 미리보기 형식을 검사한 뒤 파생본을 등록한다. 변환 중 원본이 바뀌거나 종료된 요청이면 결과를 등록하지 않는다. 동시 요청은 차단한다. 캐시는 원본 내용 해시를 포함한다.

가져온 원본은 변환 실패 전에 저장된다. 실패 이유를 버전 경고에 남기며 자동 재시도하지 않는다. 기존 가져오기와 실패한 변환은 **로컬 미리보기 준비** 명령으로 명시적으로 다시 준비할 수 있다. 명시적 재시도가 실패하면 경고를 저장하고 오류를 반환한다.

- 실제 소스 앱의 FBX 미리보기와 이후 작업: `qa-20261018-app/workflow-source.json`, `model-preview-ready.png`.
- `tests/graphics-import-preview.test.ts`: 실제 Blender FBX·BLEND 사본에서 원본 SHA 보존, 6개 원본 면/12개 삼각형 보고서, GLB/보고서 해시 등록을 확인했다. 실패 후 명시적 재시도, 잘못된 보고서, 늦은 원본 변경, 동시 요청과 종료도 검사했다.
- OBJ·STL 경로는 연결했지만 이번 실제 네이티브 검사는 FBX·BLEND에 한정한다. 임의 재질 그래프의 완전한 화면 일치까지 주장하지 않는다.

미리보기 GLB와 제작 원본의 선택도 분리했다. 뷰어 전용 파일은 화면 표시에서 사용하지만 제작·업로드·변환·Unity 전달의 원본으로 선택하지 않는다. 원본이 없는 버전을 화면 파생본만으로 처리하지 않는다. 안전 회귀 70개, API 경계 38개, 네이티브 및 관련 회귀 136개로 구성된 최종 세 배치가 모두 통과했다. 이는 244개 검사 통과이며 제품 전체의 실제 생성 품질을 의미하지 않는다. 별도의 입력 격리 집중 검사 11개도 통과했다.

근거: `qa-20261018-preview-input-safe.log`, `qa-20261018-preview-input-api.log`, `qa-20261018-preview-input-native.log`, `qa-20261018-preview-input-isolation.log`. 초기 실행 기록 `qa-20261018-preview-input-regression.log`는 실패 기록으로 보존하며, 최종 성공 기록으로 인용하지 않는다.

### 텍스처 동반 파일의 평면 검사 실패와 수정

preview.33에서 실제 텍스처 상자의 FBX+PNG 동반 파일 4개와 패킹된 BLEND 원본 각각의 미리보기를 확인했다. 원본/동반 파일 SHA와 채택 상태를 유지했다. 이 중 유효한 FBX 동반 파일 케이스는 자동 평면 검사에서 별도로 실패했다. 화면 미리보기 성공이 평면 검사 성공을 뜻하지 않는다. 초기 하네스의 동반 파일 0개 케이스는 유효한 동반 파일 증거에서 제외했고, BLEND의 종료 중단 기록은 완료된 재질 실패로 분류하지 않았다. 근거는 `qa-20261018-textured-preview/findings.json`, `report.json`이다.

원인은 평면 검사 임시 폴더에 FBX만 복사하고, 외부 텍스처를 등록·패킹하지 않은 상태에서 패킹된 원본 이미지 검사를 요구한 것이었다. 등록된 동반 이미지의 경로·크기·SHA 목록을 요청/검사/복구 identity에 고정하고, 임시 폴더에 정확한 바이트를 복사하도록 수정했다. FBX 외부 이미지 로드는 등록된 고유 파일명과 SHA를 확인한 뒤 수행하며 패킹 후에도 인코딩된 바이트 SHA를 대조한다. 미등록 이미지·중복 파일명·누락·해시 불일치와 오래된 동반 파일 검사에 의한 새 복구는 차단한다. 기존 완료 v2 후보의 과거 provenance는 유지한다. Astra나 자동 이미지 재생성은 실행하지 않는다.

기존 상자의 원본 JPG 맵 4개 바이트를 그대로 사용하는 새 FBX 사본에서 실제 네이티브 검사와 선택 평면 복구를 완료했다. 원본 면/UV/사용자 속성/노멀/다른 메시/유지 경계/재질과 이미지/교차/FBX 및 GLB 왕복 등 12개 보존 검사가 통과했다. 새 UV를 만들지 않았고 JPG 맵은 재인코딩하지 않았다. 누락 manifest, 미등록 이미지, 잘못된 해시, 중복 이름, 누락 파일의 거부도 확인했다. 근거는 `qa-20261018-textured-preview/planar-companions.json`이다.

작은 2×2 PNG와 열린 상자 메시를 사용하는 영구 네이티브 회귀 검사도 추가했다. 기존 임베디드 FBX, 임베디드 이미지와 동반 파일 충돌, 미등록/누락/해시 오류/중복 경계를 포함한 10개 검사를 확인했다. 이전/신규 회귀 검사 14개와 TypeScript 검사도 통과했다. 코드는 독립 검토에서 배포를 막는 문제를 발견하지 않았다.

수정한 최종 preview.33 배포본에서 유효한 기존 FBX 버전 `34935e0b-ffa2-4599-b7b1-e5603b395811`을 앱 버튼으로 다시 검사했다. 새 검사 `667470eb-6c18-46b9-a237-9bba325b4aff`는 review로 완료됐고, 동반 이미지 4개 목록·SHA를 보고서와 요청에 고정했다. 원본과 동반 파일 SHA, 채택 상태, 이전 실패/중단 기록 3개를 유지했다. 이 앱 검사는 새 복구 후보를 만들거나 채택하지 않았다.

같은 최종 배포본을 재시작한 뒤 작업/검사/채택 기록이 같았고 자동 재시도도 없었다. 실제 앱 재검사와 배포본 재시작 근거는 `qa-20261018-textured-preview/report.json`의 후속 검사 및 `packagedRestart`다. 최종 app.asar SHA는 `5b4bd008c1b7353e2180399c43b606bd8549f7f0311b366941fff2dc0de34800`이다.

### 후보 선택 뒤 미리보기와 실행 버튼이 화면 밖으로 이동하던 문제

결과를 바꾸거나 단계를 이동할 때 `scrollIntoView`가 숨겨진 상위 셸까지 스크롤할 수 있었다. 렌더 후 작업영역과 셸의 스크롤 위치만 조정하도록 수정했다.

### 안내 작업공간에서 Unity 대상 프로젝트 변경

연결 설정의 기본 Unity 프로젝트를 바꿔도 현재 Partsmith 프로젝트가 생성될 때 복사한 경로가 우선해, 예전 대상이 계속 검사될 수 있었다. 현재 프로젝트의 대상을 바꾸는 기능은 기존 작업실 안에만 있었다.

안내 작업공간의 Unity 단계에 대상 변경 모달을 연결했다. 경로 편집은 초안이며, 명시적으로 저장할 때 정상 Unity 프로젝트를 로컬 검사한 뒤 현재 프로젝트의 `unityPath`와 대상 프로필을 함께 갱신한다. 잘못된 경로는 기존 경로와 프로필을 유지한다. 진행·승인 대기·제출 확인 대기 작업이나 대기 중 Unity 전달이 있으면 변경을 차단한다. 기존 요청에 고정된 대상·완료 전달·GUID는 바꾸지 않는다.

실제 소스 앱에서 잘못된 경로의 거부와 격리 Unity 대상 저장을 확인했다. 엔진의 대상 변경/기존 전달 검사 20개와 UI의 안내 흐름/대상 변경 검사 2개가 통과했다. 근거는 `tests/graphics-unity-target-selection.test.ts`, `qa-20261018-ui/unity-target-final.log`, `qa-20261018-app/workflow-source.json`이다.

## 실제 앱의 상자 평면 복구와 Unity 전달

기존 상자 원본 FBX의 사본을 격리 프로필에 가져와 로컬 미리보기를 준비하고, 실제 앱의 평면 경계 검사에서 기존 큰 사각형 개구부를 선택했다. 지정한 사각형 한 개만 보완한 후보 `7627609b-d961-4125-a88c-111f761792f2`를 격리 대상에서 명시적으로 사용했다. 운영 원본과 운영 채택본에는 적용하지 않았다.

실제 앱에서 수정 후보의 Unity 대상을 확인하고, 전달 준비와 로컬 실행 승인을 따로 수행했다. 전달 ID는 `e8ceec8743a51822f74786aae9eb0393`이다. Unity 6000.3.21f1 / URP의 실제 수집 결과에서 Generated/User 프리팹을 읽었고, 메시 1개·1,923삼각형·유효하지 않은 UV 삼각형 0개를 확인했다. 폭은 2.5m이며 바닥 중심 피벗의 최소 Y는 부동소수점 오차 범위인 약 `-2.38e-7m`였다. 전달 파일 5개의 실제 SHA가 요청과 일치했다.

기존 격리 Unity 프로젝트의 보호 파일 76개 SHA는 모두 유지됐다. 최초 전달 이후 소스 앱에서 같은 전달의 완료 영수증을 수집해 `imported` 표시를 확인했다(`qa-20261018-app/workflow-source.json`).

별도로 **LOCAL UNITY REGRESSION**으로 같은 전달 ID의 재임포트를 검사했다. Generated/User GUID, 사용자 컴포넌트 값 37, 씬의 프리팹 참조, 사용자 프리팹과 씬/씬 메타 SHA를 유지했다. 최초 임포트의 Generated 파일 17개와 기존 보호 파일 76개도 변경되지 않았다. 1,923삼각형·유효하지 않은 UV 삼각형 0·폭 2.5m·바닥 중심이 유지됐다. 근거는 `qa-20261018-reimport/final.json`이다. 이 검사는 로컬 Unity 재임포트이며 앱의 재전달 버튼을 눌렀다는 증거는 아니다.

Play Mode는 실행하지 않았다. 이 상자는 무텍스처 원본이며 FBX 재질의 근사 기본색 대체 경고가 남는다. 따라서 재질 외형의 정확한 일치나 텍스처 품질, 모든 경계 복구를 확인한 것은 아니다. 근거는 `qa-20261018-app/workflow-source.json`, `qa-20261018-delivery/final.json`이다.

## Unity 자세 비교에서 확인한 것과 확인하지 못한 것

기존 자동 리깅 결과의 정확한 FBX를 격리 Unity 프로젝트에서 비교했다. 새 ARP AI는 실행하지 않았다. Unity 6000.3.21f1의 Avatar는 valid/human이었다. rest·팔·팔꿈치·왼무릎·오른무릎 각각 12,091개 렌더 정점 행의 대응을 확인했고 누락·모호 대응은 없었다.

Unity에 실제로 들어간 웨이트와 본 행렬로 계산한 변형은 Edit Mode `BakeMesh`와 작은 오차로 일치했다. 그러나 Blender 원본 웨이트와 Unity의 변형은 모든 자세에서 `2e-5` 이내로 일치하지 않았다. 팔 자세의 최대 차이는 약 `0.00018344` 원본 단위였고, Unity의 실제 최소 웨이트는 약 `0.001`이었다. 따라서 원본과 완전히 같은 웨이트 또는 완전히 같은 자세라고 기록하지 않는다.

검사는 내보낸 FBX 골격에 직접 자세 행렬을 적용한 비교다. 원래 ARP 제어 리그에서 FBX로 내보내는 전체 의미의 동등성, Humanoid 리타기팅, 게임용 클립 재생, Play Mode, 충돌, 자연스러운 관절 외형과 사용자 시각 승인은 여전히 별도 확인 사항이다.

근거: `qa-20261018-pose/comparison.json`, `final.json`. 해당 격리 Unity 프로젝트의 보호 파일 76개는 최종 해시가 유지됐다. Unity가 다시 직렬화한 QualitySettings는 기준 해시와 일치하는 보존본으로 복원했고 변경 사본을 증거에 남겼다. Unity Library 캐시는 재생성됐으며 검토용으로 보존했다. 정리 작업을 자동 실행하지 않았다.

### 깨끗한 게임 골격 동작의 별도 연구 — 앱 기능 아님

별도의 로컬 연구에서 기존 내보내기 골격 사본에 두 개의 결정적 진단 클립을 만들고, 원본 3개 파일 SHA를 유지한 채 클립 계약/합성과 FBX 자세를 검사했다. 이는 원래 ARP 제어 리그의 동작을 전달한 것이 아니며 앱에 연결한 기능도 아니다.

기존 에셋/Packages/Settings 102개와 원본 파일을 유지했다. Play Mode·게임용 Animator·원래 ARP 컨트롤러에서 FBX로의 동작 전달·최종 애니메이션 품질은 검증하지 않았다. 근거는 `qa-20261018-animation-clean/unity-final.json`이며, 앱의 신규 애니메이션 기능 완료로 집계하지 않는다.

후속 원인 검사에서는 애니메이션 클립 없이 같은 중립 자세에 `GetHumanPose`→`SetHumanPose`만 적용해도 최대 정점 차이 `0.0295647`과 약 `53.4639°`의 전완 본 회전 변화가 재현됐다. 이 결과는 해당 Avatar의 근육 자세 재구성이 원래 중립 자세를 그대로 복원하지 못한다는 근거다. Generic rest와 원래 FBX rest의 차이는 0이었다. 특정 twist/limit 설정 하나가 원인이거나 해결책이라는 결론은 아직 없으며, 단순 [-1,1] 제한 때문이라고 확정하지 않는다.

### 앱에서 내보낸 FBX의 크기 루트 정보

새 A05/X04 FBX는 custom property를 명시적으로 저장한다. FBX가 boolean 표식을 정수1로 읽는 실제 차이를 반영해 정확한 True 또는 정수1만 같은 뜻으로 해석한다. 문자열·실수·다른 값이나 오브젝트 이름으로 표식을 추측하지 않는다. FBX에서 다시 저장한 편집용 BLEND도 표식의 원래 자료형과 값을 그대로 유지한다.

표식이 있는 단일 정적 루트에만 배율 상대 FP32 오차4배(약4.77e-7)를 허용한다. 절대 오차 하한은 없으며 좌표·회전·배율을 보정하거나 초기화하지 않는다. 의미 있는 회전, 비균일·음수 배율, 임의 부모 체인·리그·동작·제약·인스턴스는 계속 차단한다.

실제 작은 A05 BLEND→새 X04 FBX→평면 검사→사각면1개 복구→저장 BLEND 재검사에서 26개 네이티브 검사를 통과했다. 기존12개 보존 검사, 변환·다른 메시·ID·원본2파일 SHA, 가로2.5m와 바닥0이 유지됐다. 1e-9/1/1e6 배율에서 오차 경계의 위·아래와 잘못된 표식도 확인했다. 기존 루트 검사16개와 관련 실행기 검사62통과·기존 환경1제외를 별도로 확인했다. 근거는 `qa-20261018-a05-fbx-roundtrip.json`과 관련 로그다. 이 결과를 모든 외부 FBX나 임의의 구멍 복구 지원으로 확대하지 않는다.

별도의 실제 앱 버튼 경로에서도 기존 작은 BLEND 가져오기→TEST 사용→배율 유지 X04 무료 승인→방금 나온 FBX를 새 오브젝트로 가져오기를 진행했다. 각 결과의 자동 평면 검사는 `review`였고, 새 FBX의 원본 해시와 검사 기록이 일치했다. 반환 FBX는 채택하지 않았다. 앞선 bulk 오브젝트의 GLB 채택·원본·실패 기록을 유지했고 재시작 후 자동 실행이 없었다. 이 앱 경로는 추가 평면 복구를 실행하지 않았으며, 위 사각면 복구는 네이티브 검증으로 구분한다. 근거는 `qa-20261018-own-fbx-roundtrip-app/report.json`이다.

## preview.39 후속 — 선택한 UV가 내보낸 파일에 연결되도록 수정

### 무료 제작 흐름에서 발견한 UV0 불일치

격리한 실제 앱에서 열린 빈 상자의 로컬 후보2개(M04)를 만들고 후보2 사용→기존 UV 유지(T02)→주황색 기본 재질(T05)→FBX·GLB 내보내기(X04)를 진행했다. 후보의 시드는 서로 다른 색을 만들며 상자 형상까지 다르다는 의미는 아니다. 참고용 합성 PNG는 이미지 연결 확인용이며 로컬 프리셋의 이미지 유사성 증거가 아니다.

편집용 BLEND는 두 번째 `Partsmith UV`를 사용했지만 FBX·GLB는 이전 `UVMap`을 UV0으로 냈다. 두 UV의 좌표가 없어지지는 않았으나, UV0을 사용하는 후속 작업은 다른 배치를 받을 수 있었다. 단색 재질이 정상으로 보인다는 이유로 전체 전달 성공으로 판단하지 않았다. 원래 실패 근거와 기존 결과는 `qa-20261018-local-chest-chain-{app,independent}`에 보존했다.

M04·T02의 기존 UV 유지·T05 및 A05·X04는 내보내기용 메시 사본에서 선택 UV를 첫 번째로 배치한다. 모든 UV 이름·모서리 좌표를 유지하며 편집용 BLEND의 순서·선택·원본 UV·재질·이미지는 바꾸지 않는다. 편집 선택과 렌더 선택이 다르면 추측하지 않고 안내한다. 텍스처 없는 UV 미지정 모델은 기존대로 내보낼 수 있다.

FBX가 선택 UV와 다른 UV의 텍스처 연결을 보존하지 못하는 경우에는 파일 출력 전에 차단하고 GLB 전용 출력을 안내한다. GLB의 명시적 다른 UV는 texCoord와 실제 이미지 바이트 보존을 확인했다. 해석할 수 없는 좌표·인스턴서·노드 그룹을 임의로 변환하지 않는다. 기존 T02 새 UV의 단일 UV 내보내기 계약, N01·Unity 및 다른 직접 GLB 호출 경로는 변경하지 않았다.
