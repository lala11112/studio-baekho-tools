# Partsmith 게임 그래픽 자동 제작 툴 전체 기획서

> Unity PC 전용 [개정 계약](04-Unity-PC-개정-구현현황.md)이 우선합니다. 기존 문서의 다른 엔진 범위는 이번 개발에서 제외합니다.

검토용 초안 1.0 · 기준일 2026년 10월 12일 · 사용자 승인 전

## 1. 제품 목표와 완료의 의미

사용자는 오브젝트와 원하는 작업을 선택하고, 필요한 조건을 자연어로 전달한다. 앱은 제작·편집·입출력·기술 검사·복구를 수행한다. 사용자는 결과를 검토하고 채택하거나 수정 지시를 한다. 수동 모델링·웨이트 페인팅·키프레임 편집·서비스 사이트 조작은 정상 제작 흐름의 필수 절차가 아니다.

‘모든 게임 그래픽’은 2D 디자인·스프라이트·UI·타일, 3D 캐릭터·무기·소품·환경, 재질, 리깅, 애니메이션, VFX, 게임 엔진용 출력까지를 포함하는 제품 범위다. 임의의 요청을 한 번에 완벽한 품질로 해결한다는 보장은 아니다. 기능마다 실제 실행·원본 회수·검토·수정·재시작 보존을 증명하고 지원 상태를 공개한다.

핵심 완료 기준:

1. 제작 명령·진행 확인·질문·비용 승인·수정·채택이 Partsmith에서 끝난다.
2. 어느 입력에서든 필요한 작업만 시작한다. 기획서 제출이나 특정 7단계를 강제하지 않는다.
3. 실행 결과가 실제 파일로 저장되고 앱에서 검토된다. 텍스트 보고나 외부 썸네일만으로 완료하지 않는다.
4. 작업 내부 처리는 자동이다. 사용자가 도구 사이의 파일 전달을 반복하지 않는다.
5. 사용자가 채택하지 않은 새 결과를 다음 제작 작업에 자동 사용하지 않는다.
6. 결과 수정은 기존 편집 가능한 결과와 필요한 참조를 이어받는다.
7. 원본·이전 버전·비용 기록을 잃지 않는다. 오류가 있어도 이미 완료된 생성부터 다시 하지 않는다.
8. GPT 사용량을 작업별로 설명할 수 있고, 품질을 낮추지 않는 낭비 감소 경로가 있다.
9. 일반 제작에서 브라우저 UI 자동화가 필요하지 않다.
10. 실제 Unity 에셋과 애니메이션·UI·효과를 각 기능의 산출물 기준으로 확인한다.

## 3. 사용자 작업 공간

### 3.1 기본 화면

- 왼쪽 **오브젝트 목록**: 폴더, 종류, 이름, 대표 결과, 작업 상태. 캐릭터와 그 무기는 별도 오브젝트로 연결 가능하다.
- 가운데 **결과 뷰어**: 이미지 확대·비교, 3D 회전·조명·와이어·UV·뼈대, 동영상·클립 타임라인, 2D 시트, 엔진 미리보기.
- 오른쪽 **작업 선택**: 대상에 맞는 작업 분류와 체크박스, 켠 작업의 설정, 입력 선택, 미충족 조건.
- 아래 **지시와 버전**: 추가 조건, 수정 대상·범위, 작업 기록, 기존 결과 비교·복원, 현재 채택 버전.
- 실행 영역 **이번 작업**: 입력 원본, 작업 범위, 처리 도구, 결과 개수, 비용, 필요한 확인, 실행 버튼.

작업 목록과 결과 채택이 긴 설정 아래에 숨지 않도록 실행·검토 영역을 유지한다. 작업 중에도 기존 채택 결과는 보여준다. 새 결과 실패로 뷰어를 빈 화면으로 바꾸지 않는다. 창 크기를 줄이면 패널을 접되 실행·오류 이유·채택 버튼은 찾을 수 있어야 한다.

### 3.2 토글의 의미

| 조작 | 의미 | 즉시 생성·과금 |
|---|---|---|
| 작업 체크 | 이번 오브젝트에서 하고 싶은 작업 추가 | 없음 |
| 설정 선택 | 단일/멀티뷰, Generic/Humanoid 등 배타적 방식 선택 | 없음 |
| 값 입력 | 개수, 면 수, 해상도, 길이 등 설정 | 없음 |
| 표시 토글 | 뼈대·와이어·배경·참조·루프 미리보기 표시 | 없음 |
| 작업 실행 | 확인된 현재 작업 시작 | 비용 승인 범위 안에서만 |
| 결과 채택 | 사용할 결과 버전 변경 | 없음 |
| 수정 실행 | 원본을 지정한 새 수정 작업 시작 | 새 범위의 비용 확인 |

모든 설정을 무조건 켜기/끄기로 만들지 않는다. 동시에 가능한 작업은 체크, 하나만 가능한 방식은 선택지, 수치는 입력란으로 표현한다. 사용자에게는 이들을 하나의 ‘작업 선택’ 패널로 제공한다.

### 3.3 선택과 자동 수행의 경계

사용자는 여러 미래 작업을 골라둘 수 있다. 앱은 필요한 연결 관계를 만든다. 기본 실행은 현재 입력이 준비된 작업 하나다. 앞 결과를 채택하면 다음 작업의 실행 버튼이 준비되지만 자동 시작하지 않는다.

한 작업 안의 업로드→제출→상태 조회→다운로드→로컬 변환→검사는 자동으로 처리한다. 리깅 안의 뼈 배치→웨이트→포즈 검사도 자동이다. 부품·본 하나씩 사람에게 확인받지 않는다. 외형·예산·대상 변경처럼 중요한 결정에서만 멈춘다.

첫 버전은 앱 전체에서 새로운 제작·편집 작업을 한 번에 하나 실행한다. 그동안 이미 제출된 원격 작업의 상태 조회·다운로드·가벼운 파일 검사는 별도 처리할 수 있다. Blender·Unity 작성은 대상 파일/프로젝트 잠금으로 직렬화하고 사용자 편집기 상태를 임의로 공유하지 않는다. 이 제한을 완화하는 병렬 제작은 추후 별도 검증 항목이다. 중복 클릭·두 앱 창에서 같은 요청 실행은 호스트의 단일 요청 잠금으로 방지한다.

선택한 모델에 표면 작업을 요청한 경우, UV가 없는 것이 확인되면 ‘UV 생성 포함’과 합산 비용을 실행 전에 표시한다. 이미 승인된 동일 작업의 내부 하위 처리를 매번 재승인시키지 않는다. UV 결과 자체를 검토하고 싶은 사용자는 UV와 텍스처를 별도 작업으로 선택할 수 있다.

## 4. 오브젝트와 참고 자료

오브젝트는 캐릭터뿐 아니라 무기, 건물, 재질, 아이콘 세트, 이펙트, 애니메이션 묶음도 될 수 있다. 한 오브젝트에 원화·모델·재질·리그·여러 동작·엔진 출력 버전이 연결된다. 다른 오브젝트의 결과는 복제하지 않고 정확한 버전을 참조할 수 있다.

모든 가져온 자료에 역할을 부여한다: **수정할 원본 / 외형 참고 / 스타일 참고 / 동작 참고 / 크기·장착 기준**. 역할은 화면에 표시한다. 캐릭터 외형 참고로 대검을 요청하면 출력 대상은 대검이다. 이미지 역할을 자동으로 ‘모델링 입력’에만 고정하지 않는다.

처음 지원할 입력: PNG/JPEG/WebP, FBX/GLB/OBJ/blend, MP4/WebM, 텍스처 세트와 안전하게 검사한 ZIP. 읽을 수 없는 형식은 변환 가능한지 먼저 안내하며 외부 경로를 몰래 복사하지 않는다. 가져온 애니메이션 FBX는 검사 후 별도 편집 blend를 만들 수 있다. 변환 결과도 출처를 보존한다.

작업 실행 시 대상 ID, 원본 버전, 참고 버전, 역할, 해시를 고정한다. 실행 중 사용자가 다른 결과를 선택해도 이미 제출한 작업의 입력은 바뀌지 않는다.

현재 채택은 오브젝트당 하나가 아니라 **역할과 항목별**로 저장한다. 디자인·모델·재질 세트·리그는 각각 채택할 수 있고, 애니메이션은 Idle·Jump 등 클립별로 여러 채택 결과를 유지한다. Idle을 채택해도 Jump나 리그 선택을 지우지 않는다. 내보내기는 모델·재질·리그·선택 클립들의 정확한 호환 조합을 하나의 고정된 묶음으로 기록한다.

## 5. 전체 작업 카탈로그와 프리셋

[전체 작업 선택표](02-전체-작업-선택표.md)의 고유 ID가 기능 범위의 기준이다. 표의 모든 작업은 앱이 실행하는 기능이다. 사용자가 외부 프로그램에서 수동으로 처리해야 하는 항목을 ‘자동 지원’으로 표시하지 않는다.

권장 프리셋:

| 프리셋 | 처음 선택할 작업 | 기본으로 선택하지 않는 작업 |
|---|---|---|
| 무기·소품 | 입력에 따라 디자인 또는 모델 생성, 표면, 크기·피벗, 내보내기 | 파츠 분리·조립·리깅·애니메이션 |
| 캐릭터 | 입력에 따라 디자인·모델, 표면, 리깅, 내보내기 | 강제 멀티뷰·강제 머리/몸통 분리·물리 |
| 환경 모듈 | 모델, 재질, 규격·스냅, 충돌체, 내보내기 | 자동 대규모 레벨 구성 |
| UI·아이콘 | 스타일 참조, 필요한 이미지, 상태·크기 정리, 출력 | 모델·리깅 |
| 2D 스프라이트 | 이미지·필요 동작, 정렬·피벗, 시트·엔진 설정 | 생성 불필요한 방향·프레임 추가 |
| VFX | 효과 종류에 따라 텍스처/메시/플립북, 효과 구성, 미리보기 | 불필요한 3D 캐릭터 공정 |

프리셋은 편집 가능한 선택 조합이며 자동 실행 명령이 아니다. 기존 모델을 가져왔을 때 새 이미지 생성이 선택되지 않도록 입력 상태를 반영한다. 사용자는 자신만의 작업 조합을 이름 붙여 저장할 수 있다.

## 6. 자연어 작업과 수정

자연어는 선택한 작업의 조건 보완 또는 목록에 없는 작업 추가 두 방식으로 사용한다. 사용자가 길게 기획서를 쓰지 않아도 현재 대상·참고·설정을 이용한다.

실행 전에 한 문장과 펼칠 수 있는 상세 항목으로 해석 결과를 보여준다. 예: ‘캐릭터 이미지 A의 검정·빨강 색감을 참고해 양손 대검 이미지 2개를 만듭니다. 캐릭터 원본은 바꾸지 않습니다.’

필수 해석 항목: 대상, 작업 종류, 입력, 바꿀 부분, 유지할 부분, 출력 종류·개수, 필요한 외부 연결, 비용 영향. 의미가 명확한 경우 반복 질문하지 않는다. 선택 오브젝트와 지시 대상이 충돌하거나, 원본 교체·유료 호출 범위가 달라지는 경우에만 앱 안에서 묻는다.

등록된 작업에 해당하면 기존 실행기로 연결한다. 새 방식이 필요하면 ‘사용자 정의 작업’으로 제한된 Codex/Blender/Unity 작업안을 만든다. 지원 도구로 할 수 없으면 비용 발생 전에 막고 가능한 범위를 제시한다. 개발자 채팅, 브라우저 조작, 플러그인 자동 설치나 전역 설정 변경을 숨은 대안으로 사용하지 않는다.

숫자로 정확히 표현된 변환은 일반 코드로 우선 처리한다. 대상이 불명확한 ‘검날만’ 같은 의미적 영역은 한 번 해석하여 표시하고 재사용한다. 영역 마스크·정점 집합·오브젝트 선택은 버전에 묶는다.

수정은 기존 편집 원본을 사용하고 새 버전으로 저장한다. 부분 재생성, 전체 새 생성, 로컬 변형은 구분한다. 서비스가 부분 편집을 지원하지 않으면 전체 생성으로 몰래 대체하지 않는다. 이미지 부분 수정의 외부 영역 보존은 마스크 합성 등 가능한 로컬 검증으로 보장하고, 완벽한 보존이 불가능하면 변경 범위를 결과와 함께 표시한다.

애니메이션 수정은 기존 액션과 채택한 동작 영상/프레임을 함께 전달한다. 영상에 보이지 않는 뒷면 움직임은 추정이라고 표시한다. 텍스트 지시를 봤다는 이유로 영상도 봤다고 기록하지 않는다.

## 7. 작업 의존 관계

의존 관계는 준비된 파일의 능력에 따라 판단하며, 특정 화면을 방문했는지로 판단하지 않는다.

| 요청 | 필요한 입력 | 없어도 되는 공정 |
|---|---|---|
| 단일 이미지 모델링 | 채택 이미지 1개 | 멀티뷰·분리 |
| 멀티뷰 모델링 | 공급자가 지원하는 방향의 채택 이미지 | 미요청 방향 생성 |
| 텍스처 | 모델과 유효 UV 또는 승인된 UV 하위 처리 | 리깅 |
| 리깅 | 변형 가능한 모델 | 원화·조립·기존 텍스처 생성 이력 |
| 3D 모션 | 호환 리그, 선택 방식에 필요한 참조 | 웹 영상이 필요 없는 방식의 새 영상 생성 |
| 동작 수정 | 기존 동작이 든 편집 장면, 지정 참조 | 정적 리그부터 재제작 |
| Unity 정적 오브젝트 | 모델·필요 재질 | 리깅·애니메이션 |
| Unity UI | 이미지와 레이아웃/슬라이스 정의 | 3D 공정 |

새 후보가 생겨도 채택 전에는 기존 결과에 영향이 없다. 채택 후에도 이전 결과는 삭제하지 않는다. 지문은 geometry, topology/vertex order, UV, material, skeleton/bind pose, action 단위로 관리한다.

- 색만 바뀌면 리그·모션을 다시 만들지 않는다. 재질을 참조하는 출력만 갱신 대상으로 표시한다.
- 메시 구조가 바뀌면 웨이트·블렌드셰이프 호환성을 검사한다.
- 뼈 계층·바인드 포즈가 바뀌면 모션과 엔진 Avatar 호환성을 검사한다.
- 클립 하나가 바뀌면 해당 클립을 포함한 출력만 이전 버전 표시한다.
- 검사로 확정할 수 없으면 ‘호환성 확인 필요’로 남긴다. 자동 삭제·생성하지 않는다.

새 요청은 호환되는 입력 조합만 실행할 수 있다. 과거 조합으로 이미 완성된 출력은 그 조합 그대로 열고 내보낼 수 있다.

## 8. 연결 방식과 실제 지원 상태

새 기본 실행 경로에서 ChatGPT/Tripo 사이트의 로그인·DOM·버튼·브라우저 다운로드 조작을 제외한다. 계정 최초 인증은 별도이며, 웹 UI 자동화를 제작 경로의 대체재로 두지 않는다.

| 실행기 | 맡을 작업 | 설계 시 확인 상태와 제한 |
|---|---|---|
| Codex 내장 이미지 | 생성·참조 편집·필요 방향 | 현재 대화에서 도구 제공. Partsmith가 실행한 작업자의 생성·원본 회수는 별도 출시 선행 검증 |
| Tripo API v3 | P2 모델·멀티뷰·UV·텍스처·지원 처리 | P2 Preview와 Smart UV 문서 존재. 실제 계정 이용·품질·요금·FBX 텍스처 전달은 새 경로로 검증 |
| Runway 공식 연결 | 측면 동작 영상·필요 영상 작업 | 기존 앱 경로의 실제 영상 생성 기록 있음. 새 오브젝트 구조에서 다시 연결 검증 |
| Blender 로컬 | 변환·검사·기본 수정·리그·애니메이션·베이크 | 확정 처리 스크립트와 Astra 작성 작업 분리. 외형·변형 품질은 결과별 검토 |
| Unity 로컬 | 에셋·재질·프리팹·UI·VFX·검사 | 원본 프로젝트를 보존하며 관리 폴더에만 반영. 수입 성공과 재생 성공을 분리 |

P2 웹 버전과 API Preview의 동일 품질, Studio의 여러 후보 묶음 요금과 API 여러 호출의 동일 비용을 가정하지 않는다. Studio 구독 크레딧은 API에 사용할 수 없다. 기능별 지원 모델·값 범위·비용 출처를 연결 어댑터가 제공한다.

Codex 내장 이미지 연결 검증 실패 시: 기존 명령의 image_generation 비활성화 범위, 공식 실행 경로, 실제 도구 가용성, 결과 이벤트·파일 반환만 좁게 진단한다. 도구가 없는 실행 환경이라면 설정 한 줄로 된다고 주장하지 않는다. 이 기능은 ‘연결 검증 필요’로 남기고 사용자가 선택할 수 있는 공식 API 대안과 별도 비용을 제시한다. 몰래 웹·다른 모델로 전환하지 않는다.

기능 상태는 **계획됨 / 문서 지원 확인 / 계정 연결 필요 / 앱 실행 검증 필요 / 사용 가능 / 일시 중단**으로 구분한다. 화면에 존재하는 토글과 실행 가능한 토글을 구분하고 비활성 이유를 표시한다.

## 9. 비용 승인과 제출 보존

작업 실행 전 비용 카드는 서비스·계정·모델·후보 수·실제 호출 수·설정·단위를 표시한다. 공식 요금 계산값은 ‘예상’, 서비스에서 받은 견적은 ‘견적’, 완료 기록은 ‘실제 사용’으로 표시한다. Tripo API 크레딧, Runway 크레딧, Codex 사용량은 합산 숫자로 섞지 않는다.

승인은 해당 작업의 입력·설정·계정·총 상한에 묶는다. 승인 범위 안의 하위 처리에는 같은 질문을 반복하지 않는다. 후보 수·서비스·비용 상한이 바뀌면 재확인한다. 취소·거절·만료 뒤 늦게 돌아온 응답은 제출 권한을 부활시키지 않는다.

제출 직전 요청과 승인, 로컬 operation ID를 먼저 저장한다. 서비스의 멱등성 기능이 문서화된 경우에만 사용한다. 실제 provider task ID가 있으면 조회·수집만 이어간다. 응답을 잃고 접수를 확인할 방법이 없으면 ‘제출 확인 필요’에서 정지한다. 예약 기록은 실제 생성·과금 성공 증거가 아니다.

사용자가 여러 결과를 원해도 서비스의 묶음 생성과 여러 독립 요청을 구분한다. 일부만 성공하면 성공한 원본부터 보존하고, 남은 작업 비용·실행 여부를 앱에 표시한다. 외형이 마음에 들지 않는 결과는 기술 오류 재시도로 취급하지 않는다.

## 10. GPT 사용량 측정과 자동 낭비 진단

개발 첫 산출물에는 기존 저장 기록으로 확인 가능한 최근 최대 10개 작업의 사용량 점검을 포함한다. 새 생성 없이 고사용량 작업을 찾아 제작·시각 판단·재시도·대기·파일 처리 구간을 구분하고, 계측 누락과 구간별 비용 귀속 불가능 범위를 명시한다. 캐시 포함 총량만 제시하지 않고 비캐시 입력·출력·재사용 가능 작업을 함께 보고한다. 매번 전체 저장소나 모든 과거 로그를 다시 스캔하지 않는다.

### 10.1 기록

작업별 실행기·모델·추론 설정·시작/완료 시각·모델 요청 수·도구 호출 수·캐시 입력·비캐시 입력·출력 토큰·보고 누락·재시도 원인·로컬 처리 시간을 저장한다. 공급자의 입력 토큰에 캐시 토큰이 포함되는지 어댑터에서 정규화하며 중복 합산하지 않는다. 한 작업자 실행과 한 모델 요청을 같은 수로 표시하지 않는다.

같은 작업 유형·모델·추론·입력 규모·출력 개수끼리 비교한다. 사용량을 계정 제한의 임의 백분율로 환산하지 않는다. 계정 잔여량을 공식 경로로 읽을 수 없으면 ‘계정 잔여량 확인 불가’라고 표시한다.

### 10.2 낭비 탐지

호스트 코드가 아래 증거를 찾아 원인과 조치 결과를 표시한다. 진단 자체를 위해 매번 GPT를 다시 호출하지 않는다.

| 신호 | 기본 조치 |
|---|---|
| 같은 입력·설정의 완료 원본 존재 | 해시·출처 검사 후 재사용을 우선 제시 |
| 대기·폴링·다운로드마다 모델 요청 발생 | 해당 구간을 호스트 상태 조회·파일 처리로 교체 대상으로 표시 |
| 같은 오류·도구 요청·상태가 반복 | 동일 작업의 무의미한 모델 재시도 차단, 마지막 원인 표시 |
| 변경 없는 큰 로그·전체 저장소를 반복 전송 | 필요한 파일·변경점·현재 작업 요약만 구성 |
| 장황한 실행 로그가 모델 문맥에 누적 | 원본 로그는 파일 보존, 모델에는 상태·오류·필수 출력만 전달 |
| 품질과 무관한 파일 변환을 모델이 작성 반복 | 검증된 로컬 실행기로 전환 |
| 이미 편집본이 있는데 처음부터 재생성 | 원본 버전 연결 누락을 표시하고 수정 요청을 막음 |

비교 가능한 정상 완료 작업이 5개 이상일 때 최근 최대 20개의 중앙값 대비 2배를 넘는 사용량을 ‘사용량 증가’로 표시한다. 이 값은 초기 진단 기준이며 품질 실패 판정이나 강제 작업 중단 기준이 아니다. 기준이 부족하면 ‘비교 자료 부족’으로 표시한다. 별도 사용자가 설정한 작업별 상한이 있으면 다음 모델 호출 전에 앱에서 재확인하며, 계측이 없는 경우 상한을 지켰다고 주장하지 않는다.

### 10.3 줄이는 방법

파일 복사·해시·크기·마스크 합성·정렬·폴링·다운로드·ffmpeg·알려진 형식 변환·결과 등록은 일반 코드가 수행한다. 시각 판단·새로운 제작·의미적 수정·리깅·애니메이션 작성 등 필요한 작업에 Codex를 사용한다. 작업별 필요한 원본 해상도와 맥락은 유지한다.

재사용 키는 입력 해시·역할·설정·모델·실행 계약 버전에 묶는다. 같은 사용자 요청이어도 입력·설정이 달라지면 재사용하지 않는다. 자격 증명과 서명 URL은 로그·모델 요약에 넣지 않는다.

앱은 검증된 낭비 감소 조치를 적용할 수 있지만 실행 중 자기 소스를 수정하거나 새 최적화 코드를 자동 배포하지 않는다. 새 최적화는 회귀 검증 후 배포한다. 모델 등급·추론 강도·참조 해상도·텍스처 품질·검수 범위를 낮추는 변경은 이 정책에 포함되지 않는다.

절감 효과는 동일 입력·설정의 적절한 비교에서 계측한 수치로만 보고한다. 비교를 위해 유료 작업을 불필요하게 다시 실행하지 않는다.

문맥 축소도 품질에 영향을 줄 수 있으므로 필수 원본·역할·보존 조건·기존 편집본·검수 결과가 그대로 전달되는 회귀 검사를 통과해야 한다. 각 최적화는 원인 증거, 적용 내용, 예상 효과, 실제 측정 효과, 품질 확인을 별도 칸에 기록한다. 예측한 절감률을 측정값으로 표시하지 않는다.

## 11. 결과 검토와 품질 규칙

모든 작업은 기술 완료와 사용자 채택을 분리한다. 검사 계약은 차단·경고·참고로 구분한다. 파일 무결성·출처·필수 입력·호환성 실패는 차단한다. 목표 면 수·쿼드 비율 편차처럼 명시적으로 허용한 항목은 실제 수치와 false 경고를 보존하면서 검토 가능하게 한다. 외형 판단은 관측된 경고와 사용자의 판단을 함께 남긴다. 경고를 숨기거나 false를 true로 바꿔 등록시키지 않는다.

| 결과 | 필수 확인 |
|---|---|
| 이미지 | 실제 원본·크기·알파·요청 개수·중복 여부·참고 연결·대상 맞음 |
| 멀티뷰 | 방향 표기·공급자 슬롯 대응·비율·중심·좌우 비대칭·후면 의미. 시트를 잘라 독립 생성물로 기록하지 않음 |
| 모델 | 실제 면·삼각환산 수·오브젝트·단위·축·실루엣·얇은 부분·메시 결함 |
| 표면 | UV·재질 슬롯·실제 텍스처 크기·경로·맵 색 공간·이음새 |
| 리그 | 뼈 계층·바인드·전체 웨이트·변형 포즈·귀/꼬리/선택 보조 대상 |
| 애니메이션 | 실제 액션·변하는 키·길이·FPS·접지·관통·루프·루트 이동·참조 일치 |
| UI·2D | 크기·피벗·9슬라이스·프레임 순서·반복 경계·텍스트·서로 다른 화면 비율 |
| VFX | 실제 엔진 효과 구성·재생·알파·정렬·입자 수/오버드로 측정, 영상만으로 대체 금지 |
| Unity | 에셋 유지·재질·Generic/Humanoid 적합성·클립/프리팹 존재. 재생 검사는 선택 시 별도 증거 |

원본은 그대로 보존하며 정렬·미리보기·엔진 사본을 구분한다. 미리보기 축소가 최종 원본 품질을 바꾸지 않는다. 맵을 실제로 만들지 않았으면 존재한다고 기록하지 않는다. 다양한 방향 영상의 동기화를 실제로 검사하지 않았다면 동기화됐다고 표시하지 않는다.

## 12. 오류 복구와 취소

정상 상태 흐름은 준비→입력/연결 확인→필요한 비용 승인→제출→처리→수집→검사→검토 대기→사용자 채택이다. 실패·사용자 확인·제출 불명·취소 요청·취소 완료·추적 중단을 별도 상태로 둔다.

- 상태 조회·일시적 네트워크 오류: 코드로 기본 2초·5초·15초 간격의 최대 3회 복구. 서비스 Retry-After가 있으면 이를 존중한다. 정상 생성 대기는 실패 재시도 횟수로 세지 않는다.
- 다운로드 오류: 같은 task ID·같은 결과만 다시 받는다. 미완료 임시 파일과 완료 파일을 구분한다.
- 로컬 변환·등록 오류: 저장 원본을 다시 검사하고 변환/등록만 실행한다.
- 모델 연결 오류: 저장된 완료 결과를 먼저 찾는다. 같은 오류로 막힌 추론 호출은 반복하지 않는다. 추가 진단은 바뀐 조건이 있을 때만 한다.
- 인증·권한·잔액·지원 안 되는 옵션: 명확한 앱 안내와 연결/설정 바로가기를 제공하고 생성은 하지 않는다.
- 앱 종료: 제출된 원격 작업의 취소까지 보장하지 않는다. 재시작 시 저장된 상태를 표시하고 조회·수집 재개는 사용자가 선택한다.
- 늦게 도착한 결과: 원본·비용 기록은 보존하되 취소된 작업을 자동 채택·진행시키지 않는다.

‘중단’ 버튼에는 실제 가능한 동작을 표시한다. 서비스 취소가 지원되지 않으면 ‘추적 중단, 서버 생성/비용은 계속될 수 있음’이라고 알린다. 상태만 바뀌지 않는 ‘복구 중’을 무기한 표시하지 않는다.

## 13. 데이터와 인터페이스

화면을 교체하더라도 기존 불변 요청·파일 해시·네이티브 제출 기록을 재사용한다. 핵심 엔터티는 다음과 같다.

| 엔터티 | 역할 |
|---|---|
| Project / Object | 프로젝트와 제작 대상, 이름·종류·관계 |
| TargetProfile | Unity 버전·렌더 파이프라인·대상 플랫폼·화면 규격·설정한 성능 예산 |
| AssetVersion | 불변 원본, 파일 목록·해시·포맷·출처·구조 지문 |
| ReferenceBinding | 대상과 참고 자료의 역할·정확한 버전 |
| TaskDefinition | 작업 ID·입력 능력·설정 규격·실행기·검사·지원 상태 |
| TaskDraft / TaskRequest | 변경 가능한 선택 설정 / 실행 시 고정한 요청 |
| ExecutionAttempt | 동일 요청의 시도·오류·사용량·복구 근거 |
| ProviderOperation | 실제 공급자 계정·요청·task ID·승인·비용·원본 회수 |
| ReviewDecision | 후보 채택·보류·거절 및 이유 |
| AcceptanceBinding | objectId·role·slotKey별 현재 채택 버전, 클립별 채택 유지 |
| DependencyEdge | 입력 버전과 의존하는 특성의 연결 |

새 IPC는 대상 조회, 작업 목록 조회, 초안 검증, 비용 확인, 실행, 취소, 조회/수집 복구, 채택, 수정, 버전 비교·복원, 사용량 조회로 분리한다. renderer가 임의 셸 명령·키·서비스 URL을 직접 실행하지 않는다.

기존 generation.quote/approve, job.poll/reconcile, workbench 요청·장부·등록기를 먼저 대응표로 정리한 뒤 새 작업 모델에 어댑터로 연결한다. 같은 요청에 두 승인 체계나 두 제출 장부를 새로 만들지 않는다. 대체가 필요한 부분은 호환성 시험을 거쳐 하나씩 전환한다.

TargetProfile은 연결한 Unity 프로젝트에서 읽은 버전·렌더 파이프라인을 기본으로 저장하고, 사용자 대상 플랫폼과 성능 예산을 추가한다. 확인 전에는 렌더러를 추정하지 않는다. 엔진 요청에는 프로필 버전을 고정하고 프로필 변경 시 재질·셰이더·UI·성능 검사 중 영향을 받는 결과만 재검토 표시한다. 엔진 패키지가 필요한 기능은 의존 항목과 변경 범위를 앱에서 먼저 보여준다.

실행기는 공통적으로 capabilities, validate, estimate, submit/run, inspect, collect, cancel-if-supported를 제공한다. 로컬 전용 작업은 유료 estimate/submit 없이 같은 결과 등록·검사를 사용한다. API는 앱 호스트에서 직접 호출하여 상태 확인용 Codex 루프를 없앤다.

TaskRequest의 최소 고정 항목: requestId, objectId, taskDefinition/version, 입력 버전·역할·해시, settings, userInstruction, outputSpec, executor/model, approvalRef, requestHash. 코드 타입·JSON schema를 단일 계약으로 공유한다. 한 작업의 settings를 다른 종류 작업에 재해석하지 않는다.

## 14. 저장과 기본 운영

프로젝트 폴더에는 원본·불변 버전·작업 기록·미리보기·내보내기를 구분한다. 인덱스와 파일의 연결은 원자적 저장/저널로 보존하고 중간 실패 후 복구할 수 있어야 한다. 상대 경로와 해시로 검증하되 외부 폴더를 임의 접근하지 않는다.

자동 저장은 설정·선택·진행 기록을 저장하는 것이며 자동 생성 명령이 아니다. 삭제는 실행 중 작업·참조 사용 여부를 확인하고 휴지통 또는 복원 가능한 프로젝트 보관함을 사용한다. 서비스 측 원본과 Unity 에셋 삭제는 별도 명시적 작업이다.

API 키는 OS 보안 저장소에서 관리한다. 계정별 파일 업로드 캐시를 분리한다. 외부 전송은 사용자가 지정한 입력만 포함한다. 참고 자료의 사용 권한·라이선스 메모를 보존할 수 있게 하되 일반 제작마다 불필요한 확인 절차를 추가하지 않는다.

폰트와 UI 문자는 가능한 한 편집 가능한 텍스트로 유지한다. 한글 파일명·긴 Windows 경로·공백·다른 드라이브를 검증한다. 임시 파일은 작업별 폴더에 격리한다. 대용량 파일은 미리보기를 늦게 읽고 캐시하되 최종 원본을 줄이지 않는다.

## 15. 기존 앱 전환

전체 교체 허용은 데이터 초기화 허용이 아니다. 현재 0.6.38의 미커밋 수정·진행 기록·외부 원본과 새 기획 변경을 먼저 구분한다. 이전 메모의 RUNNING 표기보다 실제 저장 상태를 확인한다. 실행 중인 작업을 중단·이전하거나 배포를 위해 앱을 자동 재시작하지 않는다.

새 Object/Task 계층을 기존 workbench 위에 추가하고 과거 단계·선택·서비스 장부를 읽는 호환 어댑터를 둔다. 오래된 웹 작업은 읽기·결과 검토 기록으로 보존하되 새 API 요청으로 자동 변환하지 않는다. Studio ID를 API 계정의 task ID라고 가정하지 않는다. 로컬 원본을 이용한 새 작업은 별도 출처로 연결한다.

사용자 데이터 복사본에서 마이그레이션→파일 해시·선택·비용·버전 비교→재시작을 검증한다. 라이브 전환은 작업이 없는 시점에만 수행한다. 저장 형식 버전을 올리고 구버전이 새 데이터를 덮어쓰지 못하게 한다. 롤백은 백업과 호환 읽기 경로를 사용하며 새 버전에서 생성된 결과도 보존한다.

| T24 | 공급자 옵션 불일치·권한 없음 | 유료 제출 전 명확한 중단, 저품질 대체·웹 우회 없음 |

| T26 | 중복 클릭·여러 창·공유 편집기 | 한 번 제출, 프로젝트 잠금, 늦은 결과가 다른 버전을 덮어쓰지 않음 |
| T27 | Unity 프로필 변경 | 파이프라인·버전·플랫폼 차이 표시, 다른 환경의 검증 결과 재사용 금지 |
| T28 | 문맥·토큰 최적화 | 필수 참조·보존 조건·검수 입력 유지, 예상 절감과 실제 측정 구분 |

모의 테스트, 로컬 실제 파일 검사, 서비스 실실행, 사용자 외형 채택을 별도 칸에 기록한다. 사용자가 직접 한 웹 작업을 앱 자동화 성공 증거로 합치지 않는다. 기본 UI 반응 목표는 설정·선택이 200ms 내 피드백을 보이는 것이며 생성 시간은 별도 측정한다. GPU·파일 규모·디스크 등 시험 조건을 기록하고 허위 ETA 대신 현재 작업·마지막 활동·경과 시간을 표시한다.

## 18. 검토와 변경 관리

사용자는 요약서의 7개 질문과 선택표의 ID로 유지·수정·제외·추가를 전달한다. 답이 없는 항목은 이 문서의 설계 기본값이며 승인된 사실로 바꾸지 않는다. 다음 개정에는 바뀐 항목과 영향을 표시한다. 기획 검토가 끝나기 전에는 이 문서를 근거로 유료 생성·라이브 데이터 변환을 시작하지 않는다.

개발용 지시는 [개발용 프롬프트](03-개발용-프롬프트.md)를 사용한다. 구현 시 GitHub와 기존 Notion 개발 기록에는 계획·모의 검증·실제 성공·남은 한계를 구분하여 기록한다. 이번 문서 작성은 앱 기능 구현이나 중단된 제작의 재개를 의미하지 않는다.

## 19. 확인한 연결 근거

아래는 2026년 10월 12일 확인한 공식 문서다. 기능 문서는 실제 계정 호출 성공이나 품질 보장의 근거로 확대하지 않는다.

- [OpenAI 내장 이미지 생성과 편집](https://learn.chatgpt.com/docs/image-generation): 참조 편집·내장 생성과 Codex 사용량 소비. Partsmith 작업자의 직접 연결은 별도 검증한다.
- [Tripo P Series 이미지 모델링](https://developers.tripo3d.ai/en/docs/generation-image-to-model/p): P2-20260801 Preview·쿼드·면 수 설정.
- [Tripo 변경 기록](https://developers.tripo3d.ai/en/docs/changelog): P2 멀티뷰와 Smart UV API 추가. 작업별 상세 계약은 구현 시 해당 endpoint 문서로 확정한다.
- [Tripo Studio와 API 과금 구분](https://www.tripo3d.ai/help/api-plugins/tripo-studiotripo-api): Studio 구독 크레딧을 API 호출에 사용할 수 없음.

이 문서의 자동 제작 UX, 작업 분류, 기본값, 검증 기준은 위 서비스의 보장이 아니라 Partsmith 제품 설계다.
