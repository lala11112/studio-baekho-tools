# Partsmith 자동 그래픽 제작 툴 개발용 프롬프트

검토용 초안 1.0 · 2026년 10월 12일

아래 프롬프트는 사용자가 기획·작업 목록을 검토한 뒤 개발 작업에 전달하는 용도다. 지금 붙어 있는 앱 작업을 재개하거나 과거 유료 승인을 새 제작에 사용하는 명령이 아니다. 상세 계약은 같은 폴더의 전체 기획서와 작업 선택표를 함께 전달한다.

---

Partsmith를 **사용자가 작업을 선택하면 앱이 실제 제작·수정·검사를 수행하는 게임 그래픽 자동 제작 툴**로 개발하라. 전체 화면과 작업 구조를 교체해도 된다. 그러나 기존 원본, 채택 결과, 프로젝트, 편집 가능한 파일, 비용 기록, 미완료·취소·제출 불명 작업을 삭제하거나 초기화하지 마라.

### 1. 제품의 중심

기획서 제출이나 고정된 이미지→분리→모델→리깅 순서를 시작 조건으로 삼지 마라. 사용자에게 오브젝트 작업 공간을 제공하라. 빈 대상·참고 이미지·기존 모델·텍스처·리그·동작 중 어느 것에서든 필요한 작업을 선택할 수 있어야 한다.

사용자는 오브젝트와 작업 토글, 설정, 자연어 지시를 선택하고 결과를 판단한다. 앱이 업로드, 실제 생성, 편집, 본 배치, 웨이트, 키프레임, 파일 회수, 변환, 검사, 원본 보존을 수행한다. 사용자가 Blender나 서비스 사이트에서 수동 제작을 해야 하는 것을 정상 흐름으로 만들지 마라. 기본 수동 조작은 보조 기능이다.

모든 작업은 먼저 결과를 검토 상태로 반환한다. 사용자가 채택해야 다음 작업에서 사용할 수 있다. 다음 작업은 사용자가 실행한다. 한 작업 내부의 정해진 처리·복구는 앱이 자동으로 끝낸다. 기술 처리가 끝날 때마다 자잘한 확인을 요구하지 마라.

### 2. 대상 범위

게임 디자인·참조 이미지, 2D 스프라이트·타일·아이콘·UI, 3D 캐릭터·무기·소품·환경, UV·텍스처·재질, 사람·동물·옷·머리카락 리깅, 동작 참조 영상과 3D 애니메이션, VFX·셰이더, 게임용 최적화, Unity 전달을 포함한다. 첨부한 전체 작업 선택표를 기능 목록의 기준으로 사용하라.

일반 영상 편집기나 전문 정점·브러시·키프레임 편집기를 앱 안에 새로 만들지 마라. 필요한 제작은 연결 도구가 수행하고 앱은 선택·지시·검토·관리의 중심이 된다. 첫 개발 묶음 완료를 전체 제품 완료라고 부르지 마라.

### 3. 화면과 자연어

오브젝트 목록, 실제 결과 뷰어, 작업 선택 패널, 자연어 수정, 버전 비교를 한 작업 공간에 배치하라. 작업 선택과 뼈대·와이어 같은 표시 토글을 분리하라. 체크만으로 생성·과금하지 마라. 배타적 옵션은 선택지, 수치 옵션은 입력으로 표현하라.

자료 역할을 수정 원본·외형 참고·스타일 참고·동작 참고·크기/장착 기준으로 구분하라. ‘이 캐릭터에 어울리는 대검’은 캐릭터를 참조한 새 대검 생성이다. 캐릭터를 다시 생성하거나 첨부 없이 텍스트만 보내지 마라.

목록에 없는 자연어는 실행할 대상·입력·변경/보존 범위·결과·비용을 보여주는 사용자 정의 작업으로 해석하라. 가능한 공식 도구 안에서 실행하라. 지원하지 않으면 실행 전에 이유를 말하라. 비용·대상·출력 종류가 모호할 때만 앱에서 질문하라.

### 4. 브라우저 화면을 조작하지 않는 실행

새 제작 흐름에서는 ChatGPT/Tripo 웹 UI 자동화를 사용하지 마라. 내장 로그인 창을 고치거나 Chrome 업로드·다운로드 버튼을 반복 조작하는 방식으로 돌아가지 마라. 최초 계정 인증·결제와 일상 제작을 구분하라.

이미지는 앱 소유 Codex 작업자의 내장 이미지 생성 연결을 먼저 실제 검증하라. 현재 대화에 도구가 있다는 사실을 앱 작업자에서 사용 가능한 증거로 삼지 마라. 필요한 기능이 비활성화된 실행 옵션과 공식 결과 반환 경로를 좁게 확인하라. 사용할 수 없으면 실제 한계·공식 대안·별도 비용을 제시하고 사용자의 선택을 받으라. 숨은 API 또는 다른 모델로 전환하지 마라.

모델·UV·텍스처는 Tripo 공식 API v3를 사용하라. P2 Preview·Smart UV의 문서 지원과 실제 계정 권한·가격·출력 검증을 분리하라. Studio 구독 크레딧과 API 크레딧은 별도다. 웹 P2의 후보 묶음 요금과 API 호출 비용을 동일하게 가정하지 마라.

동작 영상은 기존 Runway 공식 연결을 검증해 재사용하고, 보정·리깅·3D 동작 작성은 Blender + 사용자 지정 Astra를 사용하라. Unity·파일 작업은 가능한 한 검증된 일반 코드로 처리하라. 기존 MCP 연결을 작업 후 끄거나 전역 인증·권한 설정을 바꾸지 마라.

### 5. 파일·의존성·수정

실행 시 입력 버전·해시·역할·설정·실행기·모델·승인 범위를 고정하라. 실행 중 ‘최신 버전’으로 다시 해석하지 마라. 원본과 미리보기, 실제 생성물과 변환본, 외부 참고와 새 결과를 구분하라.

수정은 기존 편집 파일의 새 버전으로 수행하라. 애니메이션 수정에는 원래 애니메이션과 채택한 동작 영상·프레임을 계속 전달하라. 선택한 부분 수정이 미지원이면 전체 재생성으로 몰래 바꾸지 마라.

새 버전 채택으로 이전 결과를 지우지 마라. 재질 변경은 리그를 재생성할 이유가 아니며, 메시·뼈 구조 변경은 웨이트·액션 호환 검사를 요구한다. 실제 영향을 받는 결과만 오래된 입력/호환 확인 필요로 표시하라. 가져온 완성 모델·리그도 유효한 시작점으로 인정하라.

채택은 역할·항목별로 보존하라. Idle 채택이 Jump나 리그 선택을 밀어내면 안 된다. 내보내기에는 정확한 모델·재질·리그·클립 조합과 엔진 TargetProfile을 고정하라. TargetProfile은 실제 Unity 버전·렌더 파이프라인·플랫폼·화면 규격·성능 기준을 담는다.

### 6. 비용과 오류 복구

모든 추가 유료 작업은 앱에 서비스·계정·모델·입력·출력 수·실제 요청 수·금액 단위·상한을 보여주고 승인 범위 안에서만 실행하라. 공식 요금 추정, 실제 견적, 실제 차감은 구분하라. 승인된 동일 범위는 반복 확인하지 말고 변경된 범위만 재확인하라.

제출 기록을 먼저 영속 저장하고 실제 task ID가 있으면 같은 작업을 조회·수집하라. 제출 여부가 불명확하면 자동 재제출하지 마라. 다운로드나 로컬 변환 실패는 원본 재생성 없이 복구하라. 취소·거절·만료 뒤 늦게 오는 응답은 새 실행 권한이 아니다.

반복 오류에 무한 모델 호출을 하지 마라. 상태 조회·일시 통신 복구는 코드로 제한적으로 처리하고, 완료 원본부터 찾으라. 로그인·잔액·미지원 설정·사용자 결정이 필요하면 앱에서 정확한 이유와 다음 동작을 표시하라. 취소와 원격 작업 추적 중단을 구분하라.

### 7. GPT 사용량을 줄이되 품질 유지

작업별 실제 입력·캐시 입력·출력 토큰, 모델 요청과 도구 호출, 실패·대기 원인을 기록하라. 캐시 토큰의 중복 합산과 작업자 실행 수를 모델 요청 수로 오표시하지 마라. 계측하지 못한 사용량을 0이나 계정 잔여 %로 꾸미지 마라.

GPT 사용량이 커지면 먼저 원인을 확인하라. 전체 코드/로그 반복 입력, 같은 실패 재시도, 상태 확인용 추론, 이미 완성된 결과 재생성, 단순 파일 작업·수치 변환을 AI가 반복 작성하는지 검사하라. 이 검사는 호스트 코드로 우선 수행하라.

첫 개발 보고에 기존 저장 기록의 최근 최대 10개 작업을 대상으로 한 사용량 진단을 포함하라. 새 생성 없이 원인과 누락 범위를 정리하고 비캐시·캐시·출력을 구분하라. 문맥을 줄일 때 필수 참조·보존 조건·기존 편집본·검수 결과까지 누락하지 않는지 검사하라.

낭비는 필요한 문맥만 전달, 검증된 결과·업로드 재사용, 일반 코드로 파일·폴링·변환 처리, 변경 범위만 수정하는 방식으로 줄여라. 모델·추론 강도·필수 참조 해상도·결과 품질·검수 수준을 임의로 낮추지 마라. 필요한 시각 판단을 토큰 절약이라는 이유로 생략하지 마라.

앱이 사용량을 진단하되 자기 소스를 실행 중 몰래 수정하지 마라. 새 최적화는 시험·배포를 거쳐 적용하라. 절감률은 비교 측정한 범위에서만 보고하라.

### 8. 개발 순서와 증명

먼저 기존 변경·현재 작업·데이터 상태를 좁게 확인하고 보존하라. 전면 삭제·재작성부터 하지 마라. 연결 가능성을 확인한 뒤 공통 작업 공간, 정적 에셋, 캐릭터/동작, 2D/UI, 환경/VFX 순서로 검토 가능한 묶음을 완성하라.

기존 quote/approve, poll/reconcile, 장부·결과 등록·복구 구현의 대응표를 먼저 만들고 새 작업 모델은 어댑터로 연결하라. 동등한 실행 엔진·이중 장부를 따로 만들지 마라. 첫 버전의 신규 제작·편집은 앱 전체 1개이며, 상태 조회·다운로드는 분리한다. Blender/Unity 작성에는 파일·프로젝트 잠금을 적용하고 중복 실행을 검증하라.

검사는 차단·경고·참고로 구분하라. 무결성·출처·호환성은 차단하되 명시적으로 허용한 목표 면 수·쿼드 비율 편차는 실제 수치와 false 경고를 유지하여 검토할 수 있게 하라.

특히 첫 연결 통과 기준은 **앱 버튼→실제 참조를 사용한 이미지 생성→원본 저장→앱 표시→사용자 채택→재시작 후 보존**이다. 이 채팅에서 수동으로 만든 파일을 넣어서 앱 자동화 성공이라고 하지 마라. 유료 실검증은 별도 승인된 최소 범위에서만 수행하라.

단위 시험만 통과했다고 실제 제작 성공으로 보고하지 마라. 모의 검사, 실제 로컬 파일 검사, 실제 서비스 작업, 사용자 외형 채택, 실제 엔진 재생을 구분하라. 웹 화면 없이 앱만으로 무기·동물 캐릭터·2D UI·VFX 각각의 대표 시나리오를 검증하라.

Unity 기본 동작은 가져오기와 에셋 유지다. 실제 Play Mode 검사는 별도 선택이다. 기존 사용자 씬·파일은 보존하라.

마이그레이션은 데이터 복사본에서 검증하고 원본 해시·선택·작업 ID·서비스 ID·승인·비용·시도 이력을 보존하라. 진행 중 앱을 재시작하지 마라. 새 저장 형식을 구버전이 덮어쓰지 못하게 하라. 별도 배포 빌드로 검증하라.

각 묶음마다 무엇이 실제로 작동하는지, 남은 제약과 사용자 선택이 무엇인지 짧고 정확히 보고하고 GitHub·기존 Notion 기록을 갱신하라. 남은 기능을 숨기거나 ‘완벽’을 보장하는 문구로 검증을 대신하지 마라.

### 9. 반드시 멈춰야 하는 개발상의 경계

사용자가 기획을 검토 중이면 제작·과금·라이브 데이터 전환을 시작하지 마라. 본 프롬프트는 개발 범위와 품질 기준이며 기존 유료 작업의 재제출 승인이 아니다. 연결 방법의 핵심 가정이 실패하면 같은 시도를 반복하지 말고 확인한 사실과 대안을 제시하라. 기능을 지원 가능으로 표시하기 전에 실제 앱 경로를 확인하라.
